## 3.2.7 群组功能（Group）

群组是用户个人的聊天管理容器，用于分类整理聊天室和私聊联系人。群组不存储消息、不提供聊天功能。群组分为系统预设群组和用户自定义群组两类。

### 3.2.7.1 系统预设群组

#### 3.2.7.1.1 前置条件

用户已完成注册登录流程，服务端 ensure_default_groups(uid) 函数已调用执行。前端 main.html 已完整加载，群组列表页已获取到当前用户 uid。

#### 3.2.7.1.2 输入输出规范

系统预设群组由服务端在用户注册成功后自动创建，无需用户手动触发。以下为四类预设群组的定义：

| 群组 | group_id 格式 | group_type | 存储位置 | 内容来源 |
|------|-------------|------------|---------|---------|
| 课程 | sys_courses_{uid} | system | user_groups 表 | user_group_chats 关联的课程聊天室 |
| 即时聊天 | sys_im_{uid} | system | user_groups 表 | 成员动态计算为 friends 表中不存在的注册用户 |
| 私聊 | sys_private_{uid} | system | user_groups 表 | 成员动态计算为当前用户在 friends 表中的好友 |
| 未分类 | sys_uncategorized_{uid} | system | 虚拟群组（不写入数据库） | 当前用户参与过且未被 user_group_chats 引用的聊天室 |

#### 3.2.7.1.3 核心业务处理流程

**3.2.7.1.3.1 系统群组初始化**

用户注册数据入库成功后，服务端调用 ensure_default_groups(uid) 函数。课程群组写入 user_groups 表（name='课程'、group_type='system'、creator=系统预设值）。即时聊天群组写入 user_groups 表（name='即时聊天'、group_type='system'）。私聊群组写入 user_groups 表（name='私聊'、group_type='system'）。未分类群组不在 user_groups 表中写入记录，仅在前端群组列表展示时通过动态 SQL 查询生成。

**3.2.7.1.3.2 课程群组与聊天室关联**

服务端检测用户选修课程数据后，按课程名查询 groups_chat.name 字段。匹配成功时执行 INSERT INTO user_group_chats (group_id, chat_id, chat_name) VALUES (sys_courses_{uid}, 匹配chat_id, 课程名)。匹配失败时先执行 INSERT INTO groups_chat (group_id, name, creator, created_at, group_type, category) VALUES (secrets.token_hex(8), 课程名, 系统预设uid, now, 'course', '课程') 创建聊天室，再执行 user_group_chats 插入建立关联。

**3.2.7.1.3.3 成员动态计算机制**

课程群组和自定义群组的成员列表从 user_group_members 表直接读取（SELECT uid, name, role FROM user_group_members JOIN users ON uid WHERE group_id=?）。即时聊天群组的成员集合通过 SELECT uid FROM users WHERE uid != 当前用户uid AND uid NOT IN (SELECT friend_uid FROM friends WHERE uid=当前用户uid) 计算，不在 user_group_members 表中持久化。私聊群组的成员集合通过 SELECT friend_uid FROM friends WHERE uid=当前用户uid 计算，不在 user_group_members 表中持久化。

#### 3.2.7.1.4 后置条件

user_groups 表新增 group_type='system' 的三条记录（课程、即时聊天、私聊）。课程群组完成与对应课程聊天室的 user_group_chats 关联。未分类虚拟群组不产生数据库持久化记录。

#### 3.2.7.1.5 数据完整性约束

系统预设群组的 group_id 通过固定字符串模板（sys_courses_{uid}、sys_im_{uid}、sys_private_{uid}）生成，同一用户不存在重复的系统群组。系统预设群组不可通过 API 删除或修改，所有针对 group_type='system' 的写操作请求均被服务端拒绝（HTTP 403）。

### 3.2.7.2 自定义群组

自定义群组存储在 user_groups 表中（group_type='custom'），仅创建者本人可见。服务端在展示群组列表时通过 SELECT user_groups.* FROM user_groups JOIN user_group_members ON user_groups.group_id=user_group_members.group_id WHERE user_group_members.uid=当前用户uid 查询，自定义群组不会出现在非创建者的查询结果中。

#### 3.2.7.2.1 新建群组

##### 3.2.7.2.1.1 前置条件

用户已完成登录，前端群组列表页（groups.html）已加载完毕。群组列表页底部的「新建群组」按钮正常渲染。新建群组模态框的 HTML 模板已包含在页面 DOM 中（模态框 ID 为 createGroupModal）。

##### 3.2.7.2.1.2 输入输出规范

用户在群组列表页底部点击「新建群组」按钮，前端弹出新建群组模态框。用户填写以下字段：

| 字段名 | 标识符 | 类型 | 长度 | 必填 | 说明 |
|--------|--------|------|------|------|------|
| 群组名称 | createGroupNameInput | 字符串 | 1-50字符 | 是 | 群组在列表中的展示名称 |
| 分类标签 | createGroupCategorySelect | 枚举字符串 | 自定义/学习/项目/生活/兴趣 | 是 | 群组分类标识，用于前端分组展示 |

| API | 请求体 | 成功响应 | 状态码 |
|-----|--------|---------|--------|
| POST /api/user-groups | {name: string, category: string} | {message: '群组创建成功', group_id: string} | 201 |

##### 3.2.7.2.1.3 核心业务处理流程

**3.2.7.2.1.3.1 前端表单校验**

前端获取 createGroupNameInput.value，校验是否为空字符串。为空时在模态框错误提示区域展示「群组名称不能为空」，终止请求发送。前端校验字符串长度是否超过50字符。超过时在模态框错误提示区域展示「群组名称过长」，终止请求发送。

**3.2.7.2.1.3.2 服务端参数校验**

服务端接收 POST /api/user-groups 请求，解析请求体 JSON 获取 name 和 category 字段。服务端校验 name 是否为 null 或空字符串。为空时返回 HTTP 400 {error: '群组名称不能为空'}。服务端校验 name 长度是否超过50字符。超过时返回 HTTP 400 {error: '群组名称过长'}。

**3.2.7.2.1.3.3 群组标识生成**

服务端调用 group_id = secrets.token_hex(8)，生成16位十六进制随机字符串作为群组唯一标识。设置 created_at = time.time() 为当前Unix时间戳。固定设置 group_type = 'custom'、creator = 当前用户 uid。

**3.2.7.2.1.3.4 群组数据持久化**

服务端对 user_groups 表执行 INSERT，写入 group_id、name、category、group_type、creator、created_at 六个字段。服务端对 user_group_members 表执行 INSERT，写入 group_id、当前用户 uid、added_at=now。自定义群组创建时不添加除当前用户外的任何其他成员。

**3.2.7.2.1.3.5 结果反馈**

服务端返回 HTTP 201 及 {message: '群组创建成功', group_id: string}。前端接收到成功响应后调用 createGroupModal 的关闭函数隐藏模态框，调用群组列表刷新函数（GET /api/user-groups）更新列表显示。

##### 3.2.7.2.1.4 异常处理机制

| 异常场景 | 检测时机 | HTTP 状态码 | 返回信息 |
|---------|---------|------------|---------|
| 群组名称为空字符串 | 服务端参数校验阶段 | 400 | 群组名称不能为空 |
| 群组名称超过50字符 | 服务端参数校验阶段 | 400 | 群组名称过长 |
| 数据库写入失败 | 数据持久化阶段 | 500 | 系统繁忙 |

##### 3.2.7.2.1.5 后置条件

user_groups 表新增一条 group_type='custom' 的记录。user_group_members 表新增一条记录，uid 为当前用户。该群组仅创建者可见，其他用户的群组列表查询结果不包含此群组。

##### 3.2.7.2.1.6 前端交互规范

新建群组模态框的 HTML ID 为 createGroupModal，点击「新建群组」按钮时通过 JavaScript 设置模态框 display 属性为 block 以显示模态框。模态框内的名称输入框 ID 为 createGroupNameInput，分类下拉选择器 ID 为 createGroupCategorySelect，「确认创建」按钮 ID 为 createGroupSubmitBtn，「取消」按钮 ID 为 createGroupCancelBtn。点击模态框外部遮罩区域或「取消」按钮时将模态框 display 属性设置为 none 以关闭模态框。错误提示在模态框内固定错误提示区域（HTML ID 为 createGroupError）展示。创建成功后自动关闭模态框并刷新群组列表。

##### 3.2.7.2.1.7 数据完整性约束

group_id 通过 secrets.token_hex(8) 生成，碰撞概率小于 2^(-128)。user_groups 表以 group_id 为主键，数据库层面保证 group_id 唯一性。

#### 3.2.7.2.2 重命名群组

##### 3.2.7.2.2.1 前置条件

用户在群组列表中拥有至少一个自定义群组。群组详情页已加载完毕，用户具有该群组的操作权限（仅自定义群组可重命名）。

##### 3.2.7.2.2.2 输入输出规范

用户在群组列表或详情页触发重命名操作，输入新的群组名称。

| 字段名 | 标识符 | 类型 | 长度 | 必填 | 说明 |
|--------|--------|------|------|------|------|
| 群组名称 | name | 字符串 | 1-50字符 | 是 | 更新后的群组展示名称 |
| 分类标签 | category | 枚举字符串 | 自定义/学习/项目/生活/兴趣 | 否 | 更新后的分类标识 |

| API | 请求体 | 成功响应 | 状态码 |
|-----|--------|---------|--------|
| PUT /api/user-groups/{group_id} | {name: string, category: string} | {message: '更新成功'} | 200 |

##### 3.2.7.2.2.3 核心业务处理流程

**3.2.7.2.2.3.1 服务端群组存在性校验**

服务端接收 PUT /api/user-groups/{group_id} 请求，解析 path 参数 group_id。服务端执行 SELECT group_type FROM user_groups WHERE group_id=? 查询群组是否存在。查询结果为空时返回 HTTP 404 {error: '群组不存在'}。查询结果 group_type='system' 时返回 HTTP 403 {error: '系统群组不可修改'}。

**3.2.7.2.2.3.2 名称更新**

服务端执行 UPDATE user_groups SET name=?, category=? WHERE group_id=? 更新群组名称和分类。

**3.2.7.2.2.3.3 结果反馈**

服务端返回 {message: '更新成功'}。前端调用群组列表刷新函数（GET /api/user-groups）更新显示。

##### 3.2.7.2.2.4 异常处理机制

| 异常场景 | 检测时机 | HTTP 状态码 | 返回信息 |
|---------|---------|------------|---------|
| group_id 在数据库中不存在 | 服务端群组存在性校验 | 404 | 群组不存在 |
| 群组类型为 system | 服务端群组存在性校验 | 403 | 系统群组不可修改 |

##### 3.2.7.2.2.5 后置条件

user_groups 表中对应 group_id 记录的 name 和 category 字段被更新。其他与此群组关联的数据表（user_group_members、user_group_chats）不受影响。

#### 3.2.7.2.3 删除群组

##### 3.2.7.2.3.1 前置条件

用户在群组列表中拥有至少一个自定义群组。用户已确认删除操作（前端弹出确认对话框，用户点击确认）。

##### 3.2.7.2.3.2 输入输出规范

| API | 请求体 | 成功响应 | 状态码 |
|-----|--------|---------|--------|
| DELETE /api/user-groups/{group_id} | 无 | {message: '删除成功'} | 200 |

##### 3.2.7.2.3.3 核心业务处理流程

**3.2.7.2.3.3.1 服务端群组存在性与类型校验**

服务端接收 DELETE /api/user-groups/{group_id} 请求。服务端查询 group_type 判断群组类型。group_id 不存在时返回 HTTP 404。group_type='system' 时返回 HTTP 403。

**3.2.7.2.3.3.2 关联数据清除**

服务端执行 DELETE FROM user_group_chats WHERE group_id=? 清除群组与聊天室的关联关系。服务端执行 DELETE FROM user_group_members WHERE group_id=? 清除群组成员关系。

**3.2.7.2.3.3.3 群组记录删除**

服务端执行 DELETE FROM user_groups WHERE group_id=? 删除群组记录。

**3.2.7.2.3.3.4 结果反馈**

服务端返回 {message: '删除成功'}。前端从群组列表中移除该群组的显示。

##### 3.2.7.2.3.4 异常处理机制

| 异常场景 | 检测时机 | HTTP 状态码 | 返回信息 |
|---------|---------|------------|---------|
| group_id 不存在 | 群组存在性校验 | 404 | 群组不存在 |
| 群组类型为 system | 群组类型校验 | 403 | 系统群组不可删除 |

##### 3.2.7.2.3.5 后置条件

user_groups、user_group_members、user_group_chats 三表中该 group_id 关联的所有记录被删除。被删除群组关联的聊天室（groups_chat 表）不受影响，仍可独立访问。被删除群组中的成员的好友关系（friends 表）不受影响。

#### 3.2.7.2.4 向群组添加聊天室和联系人

##### 3.2.7.2.4.1 前置条件

用户在群组详情页中操作，群组类型为自定义群组（group_type='custom'）。用户至少有1个好友或参与过至少1个聊天室。添加聊天模态框已加载至页面 DOM。

##### 3.2.7.2.4.2 输入输出规范

用户在自定义群组详情页点击「添加聊天」按钮。前端弹出添加聊天模态框，该模态框分为上下两个独立区域。

| 字段名 | 标识符 | 类型 | 长度 | 必填 | 说明 |
|--------|--------|------|------|------|------|
| 成员复选框组 | memberCheckboxes | uid 字符串数组 | 每个 uid 固定长度 | 是（与聊天室复选框至少选一组） | 从好友列表中筛选出的未加入本群组的成员 |
| 聊天室复选框组 | chatCheckboxes | chat_id 字符串数组 | 每个 chat_id 固定长度 | 是（与成员复选框至少选一组） | 用户参与过但未关联本群组的聊天室 |

| API | 请求体 | 成功响应 | 状态码 |
|-----|--------|---------|--------|
| POST /api/user-groups/{group_id}/chats | {member_uids: string[], chat_ids: string[]} | {message: '添加成功'} | 200 |

##### 3.2.7.2.4.3 核心业务处理流程

**3.2.7.2.4.3.1 模态框数据加载**

前端点击「添加聊天」按钮后，先发送 GET /api/user-groups/{group_id}/detail 获取当前群组的成员列表和聊天室列表。前端发送 GET /api/friends 获取好友列表，从好友 uid 数组中排除已存在于群组成员列表中的 uid，得到可添加成员列表。前端发送 GET /api/groups（或通过 group_members 查询）获取当前用户参与的所有聊天室，从中排除已关联到本群组的 chat_id，得到可添加聊天室列表。可添加成员在模态框上方区域逐行展示（每行包含复选框和成员姓名），可添加聊天室在模态框下方区域逐行展示（每行包含复选框和聊天室名称）。

**3.2.7.2.4.3.2 用户勾选与提交**

用户勾选至少一个成员或至少一个聊天室后，点击「添加」按钮。前端收集所有被勾选的成员 uid 存入 member_uids 数组，收集所有被勾选的聊天室 chat_id 存入 chat_ids 数组。前端发送 POST /api/user-groups/{group_id}/chats，请求体为 {member_uids, chat_ids}。

**3.2.7.2.4.3.3 服务端数据处理**

服务端接收请求后，对 member_uids 数组中的每个 uid 执行 INSERT OR IGNORE INTO user_group_members (group_id, uid, added_at) VALUES (group_id, uid, now)，IGNORE 用于跳过已存在的成员记录。对 chat_ids 数组中的每个 chat_id 先查询 SELECT name FROM groups_chat WHERE group_id=chat_id 获取聊天室名称，再执行 INSERT OR IGNORE INTO user_group_chats (group_id, chat_id, chat_name) VALUES (group_id, chat_id, 查询得到的 chat_name)。

**3.2.7.2.4.3.4 结果反馈**

服务端返回 {message: '添加成功'}。前端关闭添加聊天模态框，调用群组详情刷新函数（GET /api/user-groups/{group_id}/detail）更新侧边栏成员和聊天室列表。

##### 3.2.7.2.4.4 异常处理机制

| 异常场景 | 检测时机 | HTTP 状态码 | 返回信息 |
|---------|---------|------------|---------|
| group_id 不存在 | 服务端群组校验 | 404 | 群组不存在 |
| 群组类型为 system | 服务端群组校验 | 403 | 系统群组不可修改 |
| member_uids 和 chat_ids 均为空数组 | 服务端参数校验 | 400 | 请选择要添加的成员或聊天室 |

##### 3.2.7.2.4.5 后置条件

user_group_members 表新增被勾选成员的关联记录。user_group_chats 表新增被勾选聊天室的关联记录。被添加的成员和被关联的聊天室在该群组的详情页侧边栏中显示。

##### 3.2.7.2.4.6 前端交互规范

添加聊天模态框的 HTML ID 为 addChatModal。上方成员列表区域 ID 为 addChatMemberList，下方聊天室列表区域 ID 为 addChatChatList。「添加」按钮 ID 为 addChatSubmitBtn，「取消」按钮 ID 为 addChatCancelBtn。模态框打开时前端自动加载并填充可添加成员列表和可添加聊天室列表。列表为空时对应区域展示灰色文字「暂无可选成员」或「暂无可选聊天室」。

#### 3.2.7.2.5 删除群组中的聊天室和联系人

##### 3.2.7.2.5.1 前置条件

用户在自定义群组详情页中操作，群组类型为 custom。群组详情页侧边栏中至少有一个成员（非当前用户）或至少有一个聊天室。

##### 3.2.7.2.5.2 输入输出规范

本功能支持单个删除（通过右键菜单）和批量删除（通过多选模式）两种触发方式，两种方式最终调用同一服务端接口。

| 触发方式 | 前置操作 | 界面要素 |
|---------|---------|---------|
| 单个删除（右键菜单） | 在侧边栏成员项或聊天室项上点击鼠标右键 | 弹出右键菜单，包含「详情」和「移出本群组（红色）」两个选项 |
| 批量删除（多选模式） | 点击侧边栏顶部「多选」按钮 | 每个成员项和聊天室项前出现复选框。操作栏显示「全选成员」「全选聊天室」「移出（至少勾选一项后启用）」「取消」四个按钮 |

| API | 请求体 | 成功响应 | 状态码 |
|-----|--------|---------|--------|
| POST /api/user-groups/{group_id}/batch-remove | {member_uids: string[], chat_ids: string[]} | {message: '已移出'} | 200 |

##### 3.2.7.2.5.3 核心业务处理流程

**3.2.7.2.5.3.1 右键菜单删除流程**

用户在侧边栏成员项上触发 contextmenu 事件，前端调用 showContextMenu(event, 'member', uid, name) 在鼠标位置显示右键菜单。用户在右键菜单中点击「移出本群组」选项，前端弹出 confirm 对话框显示「确认将'{name}'移出本群组？」。用户点击确认后，前端发送 POST /api/user-groups/{group_id}/batch-remove，请求体为 {member_uids: [uid], chat_ids: []}。用户在侧边栏聊天室项上触发 contextmenu 事件，前端调用 showContextMenu(event, 'chat', chatId, chatName)。聊天室移出的确认对话框显示「确认将'{chatName}'移出本群组？」，请求体为 {member_uids: [], chat_ids: [chatId]}。

**3.2.7.2.5.3.2 多选模式删除流程**

用户点击侧边栏顶部的「多选」按钮，前端为侧边栏中每项成员和聊天室添加复选框。用户点击「全选成员」按钮时，勾选侧边栏中除当前用户外的所有成员。用户点击「全选聊天室」按钮时，勾选侧边栏中所有聊天室。用户手动勾选至少一项后，「移出」按钮从禁用状态变为启用状态。用户点击「移出」按钮，前端收集所有被勾选的成员 uid 和聊天室 chat_id，发送 POST /api/user-groups/{group_id}/batch-remove。用户点击「取消」按钮时，退出多选模式，移除所有复选框，恢复侧边栏正常显示。

**3.2.7.2.5.3.3 服务端移出处理**

服务端接收 POST /api/user-groups/{group_id}/batch-remove 请求。对 member_uids 数组中的每个 uid，执行 DELETE FROM user_group_members WHERE group_id=? AND uid=?。当 uid 等于当前用户 uid 时，跳过该条删除操作（当前用户不能移出自己）。对 chat_ids 数组中的每个 chat_id，执行 DELETE FROM user_group_chats WHERE group_id=? AND chat_id=?。

**3.2.7.2.5.3.4 结果反馈**

服务端返回 {message: '已移出'}。前端调用群组详情刷新函数（GET /api/user-groups/{group_id}/detail）更新侧边栏显示。如果当前处于多选模式，退出多选模式恢复侧边栏正常显示。

##### 3.2.7.2.5.4 异常处理机制

| 异常场景 | 检测时机 | HTTP 状态码 | 返回信息 |
|---------|---------|------------|---------|
| group_id 不存在 | 服务端群组校验 | 404 | 群组不存在 |
| 群组类型为 system | 服务端群组校验 | 403 | 系统群组不可修改 |
| member_uids 和 chat_ids 均为空数组 | 服务端参数校验 | 400 | 请选择要移出的成员或聊天室 |

##### 3.2.7.2.5.5 后置条件

user_group_members 表中被移出成员的关联记录被删除，被移出成员仅从本群组中消失，该成员的好友关系（friends 表）不受影响，该成员在其他群组中的关联不受影响。user_group_chats 表中被移出聊天室的关联记录被删除，聊天室本身（groups_chat 表、group_members 表、group_messages 表）不受影响，仍可独立访问。

##### 3.2.7.2.5.6 前端交互规范

右键菜单的 HTML ID 为 ctxMenu，固定为 position:fixed 定位，z-index 为 2000，通过 display:none/block 控制显隐。右键菜单中的「详情」选项点击后调用 ctxHandleDetail() 函数，「移出本群组」选项点击后调用 ctxHandleRemove() 函数。点击页面任意非右键菜单区域时触发 document.addEventListener('click', ...) 事件处理器，隐藏右键菜单。多选模式下成员项和聊天室项上的 oncontextmenu 事件处理器被移除，右键菜单不显示。

##### 3.2.7.2.5.7 数据完整性约束

user_group_members 表中同一 group_id 和 uid 的组合通过 UNIQUE 约束或 INSERT OR IGNORE 防止重复关联。user_group_chats 表中同一 group_id 和 chat_id 的组合通过 UNIQUE 约束或 INSERT OR IGNORE 防止重复关联。批量移出操作在一个事务中执行或通过原子性 DELETE 语句保证数据一致性。

### 3.2.7.3 群组列表展示

#### 3.2.7.3.1 前置条件

用户已完成登录，前端 main.html 已加载完毕。用户拥有至少一个群组（系统群组在注册时已自动创建）。

#### 3.2.7.3.2 输入输出规范

| API | 请求体 | 成功响应 | 状态码 |
|-----|--------|---------|--------|
| GET /api/user-groups | 无 | 群组对象数组 | 200 |

每个群组对象包含字段 group_id、name、category、group_type、creator、created_at、member_count_except_self、chat_count。

member_count_except_self 的计算逻辑按群组类型区分。即时聊天群组（sys_im_{uid}）通过 SELECT COUNT(*) FROM users WHERE uid != 当前用户uid AND uid NOT IN (SELECT friend_uid FROM friends WHERE uid=当前用户uid) 计算非好友用户数量。私聊群组（sys_private_{uid}）通过 SELECT COUNT(*) FROM friends WHERE uid=当前用户uid 计算好友数量。课程群组和自定义群组通过 SELECT COUNT(*) FROM user_group_members WHERE group_id=? AND uid!=当前用户uid 计算除自己外的成员数量。chat_count 通过 SELECT COUNT(*) FROM user_group_chats WHERE group_id=? 计算关联聊天室数量。

#### 3.2.7.3.3 核心业务处理流程

**3.2.7.3.3.1 列表数据加载**

前端页面加载时自动调用 refreshGroupList() 函数，发送 GET /api/user-groups 请求获取群组列表数据。服务端查询当前用户在 user_group_members 表中的所有 group_id（包含系统群组和自定义群组），对每个群组动态计算 member_count_except_self 和 chat_count。

**3.2.7.3.3.2 前端列表渲染**

前端遍历群组数据数组，为每个群组创建一个列表项。系统群组（group_type='system'）在群组名称旁追加「系统」标签。每个列表项显示群组名称、分类标签、成员数量（「{member_count_except_self}人」）、聊天室数量（「{chat_count}个聊天室」）。群组列表按固定顺序排列：课程、即时聊天、未分类、私聊、自定义群组。

**3.2.7.3.3.3 虚拟群组生成**

前端在渲染群组列表时，检测名为 sys_uncategorized_{uid} 的虚拟群组是否需要在本次列表中出现。如果当前用户存在未被任何 user_group_chats 引用的聊天室，前端在群组列表中添加「未分类」群组项，其 chat_count 通过查询用户参与但未关联的聊天室数量计算。

#### 3.2.7.3.4 后置条件

群组列表在页面中渲染完成，每个群组项绑定点击事件。点击系统群组或自定义群组项时调用 enterGroup(group_id) 函数切换至群组详情视图。

#### 3.2.7.3.5 前端交互规范

群组列表区域的 HTML ID 为 group_list。每个群组列表项的 HTML class 为 group-item，系统群组列表项额外添加 group-item-system class。群组列表底部固定显示「新建群组」按钮（HTML ID 为 createGroupBtn）。

### 3.2.7.4 群组详情展示

#### 3.2.7.4.1 前置条件

用户在群组列表中点击了一个群组项，enterGroup(group_id) 函数已被调用。服务端存在该 group_id 对应的群组数据。

#### 3.2.7.4.2 输入输出规范

| API | 请求体 | 成功响应 | 状态码 |
|-----|--------|---------|--------|
| GET /api/user-groups/{group_id}/detail | 无 | {name, category, group_type, creator, members[], chats[]} | 200 |

成员列表中每个成员对象包含 uid、name、role 三个字段。聊天室列表中每个聊天室对象包含 chat_id、chat_name 两个字段。

成员列表的查询逻辑取决于群组类型。即时聊天群组通过 SELECT u.uid, u.name, u.role FROM users u WHERE u.uid != 当前用户uid AND u.uid NOT IN (SELECT friend_uid FROM friends WHERE uid=当前用户uid) 查询。私聊群组通过 SELECT u.uid, u.name, u.role FROM friends f JOIN users u ON f.friend_uid = u.uid WHERE f.uid = 当前用户uid 查询。自定义群组和课程群组通过 SELECT u.uid, u.name, u.role FROM user_group_members gm JOIN users u ON gm.uid = u.uid WHERE gm.group_id=? 查询。

聊天室列表的查询逻辑分为通用查询和未分类查询。通用查询通过 SELECT ugc.chat_id, ugc.chat_name, gc.name as chat_room_name FROM user_group_chats ugc LEFT JOIN groups_chat gc ON ugc.chat_id = gc.group_id WHERE ugc.group_id=? 查询。未分类虚拟群组（sys_uncategorized_{uid}）通过 SELECT gc.group_id as chat_id, gc.name as chat_name FROM group_members gm JOIN groups_chat gc ON gm.group_id = gc.group_id WHERE gm.uid = 当前用户uid AND gc.group_id NOT IN (SELECT chat_id FROM user_group_chats) 查询。

#### 3.2.7.4.3 核心业务处理流程

**3.2.7.4.3.1 详情数据加载**

前端调用 enterGroup(group_id) 函数，设置变量 selectedGroup = group_id。前端发送 GET /api/user-groups/{group_id}/detail 请求获取详情数据。服务端根据 group_id 判断群组类型，按类型执行对应的成员查询 SQL，同时执行聊天室列表查询 SQL。服务端返回群组基本信息、成员列表和聊天室列表。

**3.2.7.4.3.2 侧边栏渲染**

前端调用 renderGroupDetail() 函数渲染左侧侧边栏。侧边栏顶部显示群组名称（HTML ID 为 detailGroupName）和「返回」按钮（点击后调用 refreshGroupList() 返回群组列表）。操作栏区域显示「添加聊天」按钮、「创建聊天室」按钮、「多选」按钮。成员列表区域逐行渲染每个成员项，每项显示头像（姓名首字符）、姓名（格式为「{name}({uid})」）、角色（admin 显示「群主」、manager 显示「管理」）。聊天室列表区域逐行渲染每个聊天室项，每项显示「#」图标和聊天室名称。

**3.2.7.4.3.3 交互事件绑定**

每个成员项绑定 onclick 事件（点击时调用 startPrivateChat(uid, name) 打开弹出式私聊窗口），绑定 oncontextmenu 事件（点击右键时调用 showContextMenu(event, 'member', uid, name) 显示右键菜单）。每个聊天室项绑定 onclick 事件（点击时调用 enterChatRoom(chatId, chatName) 进入聊天室），绑定 oncontextmenu 事件（点击右键时调用 showContextMenu(event, 'chat', chatId, chatName) 显示右键菜单）。群组类型为 system 时，侧边栏中的「添加聊天」「创建聊天室」「多选」按钮隐藏或禁用，oncontextmenu 事件不绑定。

#### 3.2.7.4.4 后置条件

侧边栏在页面中渲染完成，用户可通过侧边栏执行成员私聊、进入聊天室、添加聊天室和联系人、创建聊天室、多选移出等操作。

### 3.2.7.5 右键菜单

#### 3.2.7.5.1 前置条件

群组类型为自定义群组（group_type='custom'），用户处于非多选模式。群组详情侧边栏已渲染完毕。

#### 3.2.7.5.2 交互规范

**3.2.7.5.2.1 右键菜单显示逻辑**

用户在成员项或聊天室项上触发 contextmenu 事件时，前端调用 showContextMenu(event, type, id, name) 函数。该函数将 event.preventDefault() 阻止浏览器默认右键菜单。函数读取 ctxTarget = {type, id, name} 记录当前操作目标。函数设置右键菜单元素（HTML ID 为 ctxMenu）的 left 为 event.clientX、top 为 event.clientY，将 display 设置为 block。

**3.2.7.5.2.2 详情操作**

用户点击右键菜单中的「详情」选项时，前端调用 ctxHandleDetail() 函数。该函数从全局变量 ctxTarget 读取 type、id、name。type 为 'member' 时，从 selectedGroup.members 数组中查找对应 uid 的成员数据，调用 showMemberInfo(el) 显示成员信息弹窗。type 为 'chat' 时，调用 enterChatRoom(id, name) 进入该聊天室，再调用 showChatDetail() 显示聊天室详情弹窗。

**3.2.7.5.2.3 移出操作**

用户点击右键菜单中的「移出本群组」选项（红色文字）时，前端调用 ctxHandleRemove() 函数。该函数从 ctxTarget 读取 type、id、name。前端弹出 confirm 对话框显示「确认将'{name}'移出本群组？」。用户确认后，type 为 'member' 时发送 POST /api/user-groups/{group_id}/batch-remove，请求体 {member_uids: [id]}。type 为 'chat' 时发送 POST /api/user-groups/{group_id}/batch-remove，请求体 {chat_ids: [id]}。请求成功后调用 enterGroup(selectedGroup.group_id) 刷新群组详情。

**3.2.7.5.2.4 右键菜单隐藏**

用户在页面任意非右键菜单区域点击鼠标左键时，document.addEventListener('click', ...) 事件处理器检测到 ctxMenu 的 display 为 block 且点击目标不在 ctxMenu 内部时，将 ctxMenu display 设为 none 并将 ctxTarget 设为 null。用户执行完详情或移出操作后，右键菜单自动隐藏。

### 3.2.7.6 系统群组与自定义群组的操作限制

#### 3.2.7.6.1 操作权限对照

| 操作 | 自定义群组 | 系统预设群组 |
|------|-----------|------------|
| 重命名 | 允许 | 禁止 |
| 删除 | 允许 | 禁止 |
| 添加成员 | 允许 | 禁止 |
| 批量移出成员 | 允许 | 禁止 |
| 添加聊天室关联 | 允许 | 禁止 |
| 批量移出聊天室 | 允许 | 禁止 |
| 在群组内创建聊天室 | 允许 | 禁止 |

#### 3.2.7.6.2 异常处理机制

服务端在接收群组写操作请求时，先查询 user_groups 表的 group_type 字段。group_type 为 'system' 时，直接返回 HTTP 403 {error: '系统群组不可修改'}，不执行任何数据修改操作。该校验适用于 PUT（重命名）、DELETE（删除）、POST .../chats（添加关联）、POST .../batch-remove（批量移出）、POST .../create-chat（创建聊天室）五个接口。

## 3.2.8 聊天室功能（Chat Room）

聊天室是支持多人在线实时交流的群聊空间，基于 groups_chat 表实现消息存储、成员管理、权限控制等功能。每个聊天室包含完整成员列表和消息记录。

### 3.2.8.1 创建聊天室

#### 3.2.8.1.1 在群组内创建聊天室

##### 3.2.8.1.1.1 前置条件

用户处于自定义群组（group_type='custom'）的详情页中。群组详情页的「创建聊天室」按钮正常渲染。

##### 3.2.8.1.1.2 输入输出规范

用户在自定义群组详情页点击「创建聊天室」按钮，在弹出的模态框中填写以下字段：

| 字段名 | 标识符 | 类型 | 长度 | 必填 | 说明 |
|--------|--------|------|------|------|------|
| 聊天室名称 | chatNameInput | 字符串 | 1-30字符 | 是 | 聊天室在列表和聊天界面中的展示名称 |

| API | 请求体 | 成功响应 | 状态码 |
|-----|--------|---------|--------|
| POST /api/user-groups/{group_id}/create-chat | {name: string} | {message: '聊天室创建成功', chat_id: string} | 201 |

##### 3.2.8.1.1.3 核心业务处理流程

**3.2.8.1.1.3.1 群组校验**

服务端接收 POST /api/user-groups/{group_id}/create-chat 请求。服务端查询 group_id 是否存在且 group_type 不为 system。group_id 不存在时返回 HTTP 404。group_type 为 system 时返回 HTTP 403。

**3.2.8.1.1.3.2 聊天室标识生成与数据写入**

服务端生成 chat_id = secrets.token_hex(8) 作为聊天室唯一标识。服务端对 groups_chat 表执行 INSERT，写入 chat_id、name（请求体传入）、creator（当前用户 uid）、created_at（now）、group_type（固定 'custom'）、category（继承群组的 category 字段）。

**3.2.8.1.1.3.3 创建者加入聊天室**

服务端对 group_members 表执行 INSERT，写入 group_id=chat_id、uid=当前用户 uid、role='admin'、joined_at=now，将创建者设置为群主。

**3.2.8.1.1.3.4 群组关联建立**

服务端对 user_group_chats 表执行 INSERT，写入 group_id=请求的群组group_id、chat_id=生成的chat_id、chat_name=聊天室名称，将聊天室关联到群组。

**3.2.8.1.1.3.5 系统消息写入**

服务端对 group_messages 表执行 INSERT，写入 group_id=chat_id、sender='system'、content='{当前用户name} 创建了聊天室'、timestamp=now、msg_type='system'。

**3.2.8.1.1.3.6 结果反馈**

服务端返回 HTTP 201 及 {message: '聊天室创建成功', chat_id: string}。前端关闭创建聊天室模态框，调用群组详情刷新函数。

##### 3.2.8.1.1.4 异常处理机制

| 异常场景 | 检测时机 | HTTP 状态码 | 返回信息 |
|---------|---------|------------|---------|
| 聊天室名称为空字符串 | 服务端参数校验 | 400 | 聊天室名称不能为空 |
| 群组不存在 | 服务端群组校验 | 404 | 群组不存在 |
| 群组类型为 system | 服务端群组校验 | 403 | 系统群组不可创建聊天室 |
| 数据库写入失败 | 数据写入阶段 | 500 | 系统繁忙 |

##### 3.2.8.1.1.5 后置条件

groups_chat 表新增一条 group_type='custom' 的记录。group_members 表新增一条 role='admin' 的记录（创建者）。user_group_chats 表新增一条关联记录。group_messages 表新增一条 msg_type='system' 的创建消息。

#### 3.2.8.1.2 独立创建聊天室并发送邀请

##### 3.2.8.1.2.1 前置条件

用户未在群组详情页内，或用户在创建聊天室模态框中勾选了要邀请的成员。系统的 chat_invites 表已创建。

##### 3.2.8.1.2.2 输入输出规范

用户创建聊天室时，在成员选择区域勾选要邀请的成员。成员来源为所有注册用户（SELECT uid, name FROM users WHERE uid != 当前用户uid），每个成员项左侧有一个复选框。

| API | 请求体 | 成功响应 | 状态码 |
|-----|--------|---------|--------|
| POST /api/user-groups/{group_id}/create-chat | {name: string, member_uids: string[]} | {message: '聊天室创建成功', chat_id: string} | 201 |

##### 3.2.8.1.2.3 核心业务处理流程

**3.2.8.1.2.3.1 聊天室创建**

服务端执行 3.2.8.1.1 所述聊天室创建流程（群组校验、标识生成、数据写入、创建者加入、群组关联、系统消息写入）。

**3.2.8.1.2.3.2 邀请记录写入**

服务端接收 member_uids 数组，对数组中的每个 uid 执行 INSERT INTO chat_invites (chat_id, inviter_uid, invitee_uid, status, created_at) VALUES (chat_id, 当前用户uid, 被邀请者uid, 'pending', now)。被邀请者 uid 与 chat_id 构成 UNIQUE 约束，不允许同一用户对同一聊天室存在多条 status='pending' 的邀请记录。

##### 3.2.8.1.2.4 异常处理机制

| 异常场景 | 检测时机 | HTTP 状态码 | 返回信息 |
|---------|---------|------------|---------|
| 被邀请者 uid 不存在 | 邀请记录写入 | 400 | 用户不存在 |
| 重复邀请（同用户对同聊天室已有 pending 邀请） | 邀请记录写入 | 409 | 已向该用户发送过邀请 |

##### 3.2.8.1.2.5 后置条件

chat_invites 表为每个被邀请者新增一条 status='pending' 的记录。被勾选的成员不直接加入 group_members 表。

### 3.2.8.2 聊天室邀请确认

#### 3.2.8.2.1 前置条件

被邀请用户已登录系统。chat_invites 表中存在被邀请者对应 status='pending' 的记录。

#### 3.2.8.2.2 输入输出规范

被邀请用户在通知页面（/notifications）看到待处理的聊天室邀请通知。

| API | 请求体 | 成功响应 | 状态码 |
|-----|--------|---------|--------|
| POST /api/notifications/{id}/respond | {type: 'chat_invite', action: 'accept'\|'reject'} | {message} | 200 |

#### 3.2.8.2.3 核心业务处理流程

**3.2.8.2.3.1 通知展示**

通知页面从 GET /api/notifications 获取通知列表，筛选出 type 为 chat_invite 的记录。每条通知条目显示邀请者姓名、聊天室名称、邀请时间、「同意」和「拒绝」按钮。

**3.2.8.2.3.2 同意邀请**

被邀请用户点击「同意」按钮，前端发送 POST /api/notifications/{id}/respond，请求体 {type: 'chat_invite', action: 'accept'}。服务端执行 UPDATE chat_invites SET status='accepted' WHERE id=?。服务端执行 INSERT INTO group_members (group_id, uid, role, joined_at) VALUES (chat_id, 被邀请者uid, 'member', now)，将用户以 role='member' 身份加入聊天室。服务端执行 INSERT INTO group_messages (group_id, sender, content, timestamp, msg_type) VALUES (chat_id, 'system', '{被邀请者name} 加入了聊天室', now, 'system') 写入系统消息。

**3.2.8.2.3.3 拒绝邀请**

被邀请用户点击「拒绝」按钮，前端发送 POST /api/notifications/{id}/respond，请求体 {type: 'chat_invite', action: 'reject'}。服务端执行 UPDATE chat_invites SET status='rejected' WHERE id=?，不写入 group_members 表。

#### 3.2.8.2.4 后置条件

邀请状态更新为 accepted 或 rejected。同意时被邀请者加入 group_members 表，获得聊天室访问权限并可查看聊天室消息。拒绝时不产生任何成员关系变更。

### 3.2.8.3 进入聊天室

#### 3.2.8.3.1 前置条件

用户在群组详情侧边栏中点击一个聊天室项，或通过其他方式调用 enterChatRoom(chatId, chatName) 函数。该聊天室存在于 groups_chat 表中。

#### 3.2.8.3.2 核心业务处理流程

**3.2.8.3.2.1 界面切换**

前端调用 enterChatRoom(chatId, chatName) 函数。函数从侧边栏所有聊天室项中移除 active 高亮 class，为当前点击的聊天室项添加 active 高亮 class。函数将右侧聊天界面顶部的标题（HTML ID 为 currentChatName）设置为聊天室名称。函数将「... 详情」按钮显示在标题旁。函数将消息输入区域（HTML ID 为 inputBar）由 display:none 改为 display:flex。

**3.2.8.3.2.2 消息加载**

函数调用 loadGroupMessages() 加载聊天室消息。初次加载时，消息容器（HTML ID 为 chatMessages）显示「加载中...」。函数发送 GET /api/groups/{chatId}/messages 请求。服务端返回消息数组，每条消息包含 sender、sender_name、content、timestamp、msg_type 字段。

**3.2.8.3.2.3 消息渲染**

前端遍历消息数组逐条渲染。msg_type='system' 的消息渲染为居中灰色文字，无消息气泡、无发送者头像。sender 等于当前用户 uid 的消息渲染为右侧气泡（白色背景、蓝色边框、右对齐）。sender 不等于当前用户 uid 的消息渲染为左侧气泡（灰色背景、左对齐），气泡上方显示发送者姓名，姓名左侧显示头像（姓名首字符）。接口调用失败时，消息容器显示错误详情文字。

**3.2.8.3.2.4 轮询启动**

函数启动一个 setInterval 定时器，间隔为 2000 毫秒，持续调用 loadGroupMessages() 获取新消息。函数检测之前是否存在私聊轮询定时器（privatePollTimer），如果存在则调用 clearInterval(privatePollTimer) 清除。

#### 3.2.8.3.3 后置条件

右侧聊天界面切换为当前聊天室的显示状态。消息区域显示聊天室消息列表。轮询定时器运行，持续更新消息。

### 3.2.8.4 聊天室消息发送

#### 3.2.8.4.1 前置条件

用户已进入聊天室（enterChatRoom 已调用）。消息输入区域（inputBar）处于可见状态。

#### 3.2.8.4.2 输入输出规范

| API | 请求体 | 成功响应 | 状态码 |
|-----|--------|---------|--------|
| POST /api/groups/{chatId}/send | {content: string} | {message} | 200 |

#### 3.2.8.4.3 核心业务处理流程

**3.2.8.4.3.1 输入校验**

用户在消息输入框（HTML ID 为 chatInput）中输入文字，按 Enter 键或点击发送按钮（HTML ID 为 sendBtn）。前端获取 chatInput.value，校验是否为空字符串。为空时不做处理。前端校验字符串长度是否超过2000字符。超过时前端弹出提示「消息长度不能超过2000字符」，阻止发送。

**3.2.8.4.3.2 乐观渲染**

前端直接将消息内容追加到消息列表末尾，渲染为右侧气泡样式（与 3.2.8.3.2.3 所述自己消息的渲染规则一致），然后调用 scroll 函数将消息容器滚动到底部。

**3.2.8.4.3.3 服务端写入**

前端发送 POST /api/groups/{chatId}/send，请求体 {content: 消息内容}。服务端执行 INSERT INTO group_messages (group_id, sender, content, timestamp, msg_type) VALUES (chatId, 当前用户uid, content, now, 'text')。

**3.2.8.4.3.4 输入框清空**

前端将 chatInput.value 设置为空字符串。

### 3.2.8.5 聊天室详情

#### 3.2.8.5.1 前置条件

用户已进入聊天室或右键聊天室项后点击「详情」。服务端返回聊天室详情数据。

#### 3.2.8.5.2 输入输出规范

| API | 请求体 | 成功响应 | 状态码 |
|-----|--------|---------|--------|
| GET /api/groups/{chatId}/detail | 无 | {name: string, creator: string, members: [{uid, name, role, joined_at}]} | 200 |

#### 3.2.8.5.3 核心业务处理流程

**3.2.8.5.3.1 详情弹窗打开**

前端通过聊天界面右上角「... 详情」按钮或群组侧边栏右键聊天室后点击「详情」触发 showChatDetail() 函数。函数发送 GET /api/groups/{chatId}/detail 请求获取聊天室详细信息。函数打开聊天室详情弹窗（HTML ID 为 chatDetailModal）。

**3.2.8.5.3.2 详情信息渲染**

弹窗最上方显示聊天室名称。名称下方显示元数据文字「{成员数} 位成员 · 创建者: {创建者姓名}」。成员列表逐行渲染，每行显示头像（姓名首字符）、姓名、role 标签（admin 显示「🔑群主」、manager 显示「🛡️管理员」、member 不显示标签）。当成员的 uid 等于当前用户 uid 时，在姓名旁显示「（我）」标签。

**3.2.8.5.3.3 操作按钮显示**

当前用户 role 为 admin 或 manager 时显示重命名按钮和公告按钮。当前用户 role 为 admin 时显示解散聊天室按钮。弹窗底部显示「邀请成员」按钮和「退出聊天室」按钮。对于当前用户 role 为 admin 的聊天室，每个 role 不为 admin 的成员项旁显示「踢出」按钮和「设为管理」或「取消管理」按钮（成员 role 为 manager 时显示「取消管理」，成员 role 为 member 时显示「设为管理」）。

#### 3.2.8.5.4 重命名聊天室

##### 3.2.8.5.4.1 前置条件

当前用户在聊天室中的 role 为 admin 或 manager。聊天室详情弹窗已打开。

##### 3.2.8.5.4.2 输入输出规范

用户在详情弹窗中点击重命名按钮，输入新名称。

| 字段名 | 标识符 | 类型 | 长度 | 必填 | 说明 |
|--------|--------|------|------|------|------|
| 聊天室名称 | renameChatInput | 字符串 | 1-30字符 | 是 | 更新后的聊天室名称 |

| API | 请求体 | 成功响应 | 状态码 |
|-----|--------|---------|--------|
| PUT /api/groups/{chatId}/rename | {name: string} | {message: '重命名成功'} | 200 |

处理流程：服务端执行 UPDATE groups_chat SET name=? WHERE group_id=?。服务端返回 {message: '重命名成功'}。前端更新本地聊天室名称显示（更新 currentChatRoom、侧边栏聊天室项名称、详情弹窗标题）。

##### 3.2.8.5.4.3 异常处理机制

| 异常场景 | 检测时机 | HTTP 状态码 | 返回信息 |
|---------|---------|------------|---------|
| 名称为空 | 服务端参数校验 | 400 | 聊天室名称不能为空 |
| 当前用户 role 不足 | 服务端权限校验 | 403 | 无权限重命名 |

#### 3.2.8.5.5 发布公告

##### 3.2.8.5.5.1 前置条件

当前用户在聊天室中的 role 为 admin 或 manager。聊天室详情弹窗已打开。

##### 3.2.8.5.5.2 输入输出规范

| 字段名 | 标识符 | 类型 | 长度 | 必填 | 说明 |
|--------|--------|------|------|------|------|
| 公告内容 | announcementInput | 字符串 | 1-500字符 | 是 | 公告展示内容 |

| API | 请求体 | 成功响应 | 状态码 |
|-----|--------|---------|--------|
| POST /api/groups/{chatId}/announcement | {content: string} | {message: '公告发布成功'} | 200 |

处理流程：服务端将公告内容存储到 groups_chat 表的 announcement 字段。服务端返回 {message: '公告发布成功'}。前端在聊天界面顶部显示公告横幅，横幅包含公告内容和关闭按钮。用户点击关闭后，该公告的群组 id 存入 localStorage，下次进入该聊天室时不再显示该公告。

##### 3.2.8.5.5.3 异常处理机制

| 异常场景 | 检测时机 | HTTP 状态码 | 返回信息 |
|---------|---------|------------|---------|
| 公告内容为空 | 服务端参数校验 | 400 | 公告内容不能为空 |
| 当前用户 role 不足 | 服务端权限校验 | 403 | 无权限发布公告 |

#### 3.2.8.5.6 邀请成员

##### 3.2.8.5.6.1 前置条件

当前用户是聊天室成员（role 不限）。聊天室详情弹窗已打开。存在非本聊天室成员的其他注册用户。

##### 3.2.8.5.6.2 输入输出规范

| API | 请求体 | 成功响应 | 状态码 |
|-----|--------|---------|--------|
| POST /api/groups/{chatId}/invite | {member_uids: string[]} | {message: '邀请已发送'} | 200 |

处理流程：前端弹出邀请模态框，展示所有注册用户中不在本聊天室成员列表中的用户（SELECT uid, name FROM users WHERE uid NOT IN (SELECT uid FROM group_members WHERE group_id=chatId)），每人左侧有一个复选框。用户勾选后点击邀请按钮，前端发送 POST /api/groups/{chatId}/invite。服务端对 member_uids 数组中每个 uid 执行 INSERT INTO chat_invites (chat_id, inviter_uid, invitee_uid, status, created_at) VALUES (chatId, 当前用户uid, uid, 'pending', now)。服务端返回 {message: '邀请已发送'}。

##### 3.2.8.5.6.3 异常处理机制

| 异常场景 | 检测时机 | HTTP 状态码 | 返回信息 |
|---------|---------|------------|---------|
| member_uids 数组为空 | 服务端参数校验 | 400 | 请选择要邀请的成员 |

#### 3.2.8.5.7 踢出成员

##### 3.2.8.5.7.1 前置条件

当前用户在聊天室中的 role 为 admin。聊天室详情弹窗已打开。目标成员 role 不为 admin。

##### 3.2.8.5.7.2 输入输出规范

| API | 请求体 | 成功响应 | 状态码 |
|-----|--------|---------|--------|
| POST /api/groups/{chatId}/kick | {uid: string} | {message} | 200 |

处理流程：服务端执行 DELETE FROM group_members WHERE group_id=? AND uid=?，DELETE 语句的条件中不包含 role='admin' 的用户（不允许踢出群主）。服务端执行 INSERT INTO group_messages (group_id, sender, content, timestamp, msg_type) VALUES (chatId, 'system', '{成员name} 已被移出聊天室', now, 'system')。服务端返回成功响应。前端刷新成员列表。

##### 3.2.8.5.7.3 异常处理机制

| 异常场景 | 检测时机 | HTTP 状态码 | 返回信息 |
|---------|---------|------------|---------|
| 目标用户 role 为 admin | 服务端执行阶段 | 403 | 不能移出群主 |
| 当前用户 role 不为 admin | 服务端权限校验 | 403 | 无权限踢出成员 |

#### 3.2.8.5.8 设置或取消管理员

##### 3.2.8.5.8.1 前置条件

当前用户在聊天室中的 role 为 admin。聊天室详情弹窗已打开。目标成员 role 为 member（设置时）或 manager（取消时）。

##### 3.2.8.5.8.2 输入输出规范

| API | 请求体 | 成功响应 | 状态码 |
|-----|--------|---------|--------|
| POST /api/groups/{chatId}/admin | {uid: string, action: 'set'|'unset'} | {message} | 200 |

处理流程：action='set' 时服务端执行 UPDATE group_members SET role='manager' WHERE group_id=? AND uid=?。action='unset' 时服务端执行 UPDATE group_members SET role='member' WHERE group_id=? AND uid=?。服务端返回成功响应。前端更新成员列表中该成员的 role 显示。

#### 3.2.8.5.9 退出聊天室

##### 3.2.8.5.9.1 前置条件

当前用户是聊天室成员，且 role 不为 admin。

##### 3.2.8.5.9.2 输入输出规范

| API | 请求体 | 成功响应 | 状态码 |
|-----|--------|---------|--------|
| POST /api/groups/{chatId}/leave | 无 | {message} | 200 |

处理流程：服务端执行 DELETE FROM group_members WHERE group_id=? AND uid=?。如果当前用户 role 为 admin，DELETE 操作不被执行，返回 HTTP 403。服务端在删除后查询 SELECT COUNT(*) FROM group_members WHERE group_id=?。如果成员数小于2，执行自动解散逻辑（同 3.2.8.5.11）。

##### 3.2.8.5.9.3 异常处理机制

| 异常场景 | 检测时机 | HTTP 状态码 | 返回信息 |
|---------|---------|------------|---------|
| 当前用户 role 为 admin | 服务端权限校验 | 403 | 群主不能退出聊天室 |

#### 3.2.8.5.10 解散聊天室

##### 3.2.8.5.10.1 前置条件

当前用户在聊天室中的 role 为 admin。用户在详情弹窗中点击「解散聊天室」按钮后，弹出的确认对话框已被用户确认。

##### 3.2.8.5.10.2 输入输出规范

| API | 请求体 | 成功响应 | 状态码 |
|-----|--------|---------|--------|
| POST /api/groups/{chatId}/dissolve | 无 | {message} | 200 |

##### 3.2.8.5.10.3 核心业务处理流程

服务端接收解散请求后，按以下顺序执行数据库操作。第一，INSERT INTO group_messages (group_id, sender, content, timestamp, msg_type) VALUES (chatId, 'system', '聊天室已被解散', now, 'system') 写入解散消息。第二，DELETE FROM user_group_chats WHERE chat_id=? 清除所有群组对该聊天室的关联。第三，DELETE FROM group_members WHERE group_id=? 删除所有成员关系。第四，DELETE FROM groups_chat WHERE group_id=? 删除聊天室本身。group_messages 表中的消息记录不被删除，保留消息历史。

##### 3.2.8.5.10.4 后置条件

groups_chat 表中该聊天室的记录被删除。group_members 表中该聊天室的所有成员关系被删除。user_group_chats 表中该聊天室的关联被删除。所有群组的侧边栏中将不再显示该聊天室。

#### 3.2.8.5.11 自动解散

##### 3.2.8.5.11.1 触发条件

每次聊天室成员执行退出（3.2.8.5.9）或踢出（3.2.8.5.7）操作后，服务端执行 SELECT COUNT(*) FROM group_members WHERE group_id=?。如果计数小于2，触发自动解散逻辑。

##### 3.2.8.5.11.2 处理流程

服务端执行与 3.2.8.5.10 一致的解散流程，但系统消息内容为「聊天室人员只剩一人，已自动解散」。

### 3.2.8.6 聊天室角色

| role 值 | 名称 | 获得方式 | 权限集合 |
|---------|------|---------|---------|
| admin | 群主 | 创建聊天室时自动获得 | 踢出成员、设置或取消管理员、重命名、发布公告、解散聊天室 |
| manager | 管理员 | 由 admin 通过设置管理员操作（3.2.8.5.8）授予 | 重命名、发布公告 |
| member | 普通成员 | 通过邀请确认后加入（3.2.8.2.3.2） | 邀请成员、退出聊天室 |

#### 3.2.8.6.1 数据完整性约束

group_members 表中同一 group_id 和 uid 的组合通过 PRIMARY KEY(group_id, uid) 或 UNIQUE 约束防止重复加入。chat_invites 表中同一 chat_id 和 invitee_uid 的组合不允许存在多条 status='pending' 的记录。

## 3.2.9 私聊功能（Private Chat）

私聊功能支持用户之间进行一对一文本消息交流，基于 messages 表存储消息数据。

### 3.2.9.1 发起私聊

#### 3.2.9.1.1 前置条件

用户在群组详情侧边栏中点击一个成员项（非多选模式下），或通过其他方式（如成员信息弹窗中的「发消息」按钮）触发私聊。弹出式私聊模态框的 HTML 模板已包含在页面 DOM 中。

#### 3.2.9.1.2 输入输出规范

| 触发方式 | 触发位置 | 调用函数 |
|---------|---------|---------|
| 群组侧边栏点击成员项 | 群组详情页侧边栏成员列表 | startPrivateChat(uid, name) |
| 成员信息弹窗「发消息」按钮 | 成员信息弹窗 | startPrivateChat(uid, name) |

#### 3.2.9.1.3 核心业务处理流程

**3.2.9.1.3.1 私聊窗口打开**

前端调用 startPrivateChat(uid, name) 函数。函数将弹出式私聊模态框（HTML ID 为 popupChatModal）的 display 设置为 block。函数设置模态框顶部标题栏显示「💬 {对方姓名}」。函数在标题栏旁显示「返回」按钮（点击后将模态框 display 设为 none）和「... 详情」按钮。函数将底部消息输入框（HTML ID 为 popupChatInput）和发送按钮（HTML ID 为 popupSendBtn）设置为可见。

**3.2.9.1.3.2 消息加载**

函数调用 loadPrivateMessages(uid) 加载与该用户的私聊消息。函数发送 GET /api/messages?uid={对方uid} 请求。服务端返回当前用户与对方用户之间的消息数组，按 timestamp 升序排列。每条消息包含 id、sender、receiver、content、timestamp、is_revoked 字段。

**3.2.9.1.3.3 备忘录功能判断**

如果对方 uid 等于当前用户 uid，标题栏显示「💬 与我聊天」（作为备忘录功能）。其他流程与普通私聊一致。

**3.2.9.1.3.4 轮询启动**

函数启动一个 setInterval 定时器，间隔为 2000 毫秒，持续调用 loadPrivateMessages(uid) 获取新消息。函数检测之前是否存在群聊轮询定时器（groupPollTimer），如果存在则调用 clearInterval(groupPollTimer) 清除。

#### 3.2.9.1.4 前端交互规范

弹出式私聊模态框的 HTML ID 为 popupChatModal。消息列表区域 ID 为 popupChatMessages。消息输入框 ID 为 popupChatInput。发送按钮 ID 为 popupSendBtn。私聊消息支持按 Enter 键发送（在 popupChatInput 上监听 keydown 事件，keyCode 为 13 时触发送）。弹出式私聊窗口可与其他弹出式模态框（如成员信息弹窗）同时存在。

### 3.2.9.2 私聊消息

#### 3.2.9.2.1 输入输出规范

| API | 请求体/参数 | 成功响应 | 状态码 |
|-----|------------|---------|--------|
| GET /api/messages | 查询参数 uid=对方uid | 消息数组（按 timestamp 升序） | 200 |
| POST /api/send | {receiver: string, content: string} | {message} | 200 |

#### 3.2.9.2.2 核心业务处理流程

**3.2.9.2.2.1 消息获取**

前端发送 GET /api/messages?uid={对方uid}。服务端执行 SELECT * FROM messages WHERE (sender=当前用户uid AND receiver=对方uid) OR (sender=对方uid AND receiver=当前用户uid) ORDER BY timestamp ASC 返回消息列表。

**3.2.9.2.2.2 消息渲染**

前端遍历消息数组逐条渲染。sender 等于当前用户 uid 的消息气泡样式为靠右（白色背景、蓝色边框）。sender 等于对方 uid 的消息气泡样式为靠左（灰色背景）。每条消息上方显示发送者姓名和头像（姓名首字符）。is_revoked 等于 1 的消息，内容显示为「对方撤回了一条消息」（对方发送的消息）或「你撤回了一条消息」（自己发送的消息），该文字为灰色斜体。自己的消息下方显示「已读」标记（当前版本始终显示为已读状态，灰色文字）。

**3.2.9.2.2.3 消息发送**

用户在 popupChatInput 中输入文字，按 Enter 键或点击 popupSendBtn。前端校验内容是否为空字符串，为空时不做处理。前端校验内容长度是否超过2000字符，超过时弹出提示「消息长度不能超过2000字符」并阻止发送。前端发送 POST /api/send，请求体 {receiver: 对方uid, content: 消息内容}。服务端执行 INSERT INTO messages (sender, receiver, content, timestamp) VALUES (当前用户uid, 对方uid, content, now)。前端将消息追加到消息列表末尾（乐观渲染），滚动到底部，将输入框置空。

#### 3.2.9.2.3 异常处理机制

| 异常场景 | 检测时机 | HTTP 状态码 | 返回信息 |
|---------|---------|------------|---------|
| 消息内容为空 | 服务端参数校验 | 400 | 消息不能为空 |
| 消息内容超过2000字符 | 前端校验/服务端校验 | 400 | 消息长度不能超过2000字符 |

### 3.2.9.3 消息撤回

#### 3.2.9.3.1 前置条件

待撤回消息的发送者为当前用户（sender=当前用户uid）。消息发送时间与当前时间的差值小于120秒。

#### 3.2.9.3.2 输入输出规范

| API | 请求体 | 成功响应 | 状态码 |
|-----|--------|---------|--------|
| POST /api/messages/revoke/{messageId} | 无 | {message: '撤回成功'} | 200 |

#### 3.2.9.3.3 核心业务处理流程

服务端执行 UPDATE messages SET is_revoked=1 WHERE id=? AND sender=当前用户uid AND ? - timestamp < 120。UPDATE 语句中的 WHERE 条件同时校验发送者身份（sender=当前用户uid）和时间窗口（当前时间减timestamp小于120秒）。服务端检查 UPDATE 影响的行数，影响行数为0时根据具体原因返回对应错误，影响行数大于0时返回 {message: '撤回成功'}。前端调用消息刷新函数，被撤回消息的内容显示为「你撤回了一条消息」。

#### 3.2.9.3.4 异常处理机制

| 异常场景 | 检测时机 | HTTP 状态码 | 返回信息 |
|---------|---------|------------|---------|
| 消息发送时间超过2分钟 | 服务端时间窗口校验 | 400 | 超过撤回时间 |
| 当前用户不是消息发送者 | 服务端身份校验 | 403 | 无权撤回 |

### 3.2.9.4 私聊详情

#### 3.2.9.4.1 前置条件

弹出式私聊窗口已打开。窗口中有对话中的对方用户。

#### 3.2.9.4.2 交互规范

在弹出式私聊窗口中，点击顶部对方姓名旁的「... 详情」按钮，前端调用 showMemberInfoFromPrivate() 函数。该函数构造数据集 {uid: 对方uid, name: 对方name, role: ''}，传入 showMemberInfo(el) 函数。showMemberInfo(el) 函数打开成员信息弹窗（HTML ID 为 memberInfoModal）并展示对方用户的详细信息。

### 3.2.9.5 成员信息界面

#### 3.2.9.5.1 触发方式

成员信息弹窗通过以下五种方式触发，所有触发方式最终调用 showMemberInfo(el) 函数：

| 触发方式 | 触发位置 | 传入数据集中的 uid 和 name 来源 |
|---------|---------|-------------------------------|
| 群组侧边栏右键成员后点击「详情」 | 群组详情页侧边栏 | ctxTarget 中的 id 和 name |
| 聊天室详情弹窗中点击成员项 | 聊天室详情弹窗成员列表 | 成员项的 dataset.uid 和 dataset.name |
| 群聊消息发送者姓名或头像上的点击或右键 | 聊天室消息列表 | 消息数据中的 sender uid 和 sender_name |
| 私聊消息发送者姓名或头像上的点击或右键 | 私聊消息列表 | 消息数据中的 sender uid 和 sender_name |
| 私聊窗口右上角「... 详情」按钮 | 弹出式私聊窗口 | showMemberInfoFromPrivate() 构造的数据 |

#### 3.2.9.5.2 输入输出规范

| API | 请求体 | 成功响应 | 状态码 |
|-----|--------|---------|--------|
| GET /api/user/{uid} | 无 | {uid: string, name: string, role: string, description: string} | 200 |

#### 3.2.9.5.3 交互规范

成员信息弹窗显示以下内容。头像区域显示成员姓名的第一个字符作为头像（圆形、大号字体）。成员详细信息区域显示姓名（name 字段值）、学号或工号（uid 字段值）、角色（role 字段值的中文映射：student→学生、teacher→教师、manager→管理员）。个人简介区域显示 description 字段值，description 为空字符串时显示「暂无简介」（灰色文字）。

「发消息」按钮位于信息区域下方，点击后关闭成员信息弹窗，调用 startPrivateChat(uid, name) 打开与该用户的弹出式私聊窗口。

好友状态区域显示「加好友」按钮或「已是好友」标签。前端调用 GET /api/friends 获取好友列表，判断该 uid 是否在好友列表中。不在列表中时显示「加好友」按钮。在列表中时显示「已是好友」标签（灰色文字，不可点击）。如果该用户已发送过好友申请且 status='pending'，显示「已申请」标签（灰色文字，不可点击）。

黑名单状态区域显示「拉黑」按钮（红色文字）或「取消拉黑」按钮。前端调用 GET /api/blacklist 获取黑名单列表，判断该 uid 是否在黑名单中。不在黑名单中时显示「拉黑」按钮。在黑名单中时显示「取消拉黑」按钮。

### 3.2.9.6 加好友流程

#### 3.2.9.6.1 前置条件

用户在成员信息弹窗中查看的成员 uid 不在当前用户的好友列表中。当前用户未向该成员发送过 status='pending' 的好友申请。

#### 3.2.9.6.2 输入输出规范

| 字段名 | 标识符 | 类型 | 长度 | 必填 | 说明 |
|--------|--------|------|------|------|------|
| 申请说明 | friendRequestInput | 字符串 | 1-100字符 | 是 | 添加好友时的申请理由 |

| API | 请求体 | 成功响应 | 状态码 |
|-----|--------|---------|--------|
| POST /api/friends/add | {uid: string, message: string} | {message: '好友申请已发送'} | 200 |

#### 3.2.9.6.3 核心业务处理流程

**3.2.9.6.3.1 申请模态框打开**

用户在成员信息弹窗中点击「加好友」按钮，前端弹出填写申请说明的模态框（HTML ID 为 friendRequestModal）。模态框包含说明输入框（HTML ID 为 friendRequestInput，placeholder 为「请输入申请说明」）和「发送」按钮（HTML ID 为 friendRequestSubmitBtn）和「取消」按钮。

**3.2.9.6.3.2 申请提交**

用户填写说明后点击「发送」。前端发送 POST /api/friends/add，请求体 {uid: 对方uid, message: 申请说明}。服务端在 friend_requests 表中插入一条记录，字段为 from_uid=当前用户uid、to_uid=对方uid、status='pending'、created_at=now、message=申请说明。

**3.2.9.6.3.3 申请反馈**

服务端返回 {message: '好友申请已发送'}。前端关闭 friendRequestModal。成员信息弹窗中的「加好友」按钮变为「已申请」标签（灰色文字，不可点击）。如果同一用户再次打开同一成员的成员信息弹窗，前端检测到 friend_requests 表中存在 from_uid=当前用户uid AND to_uid=对方uid AND status='pending' 的记录，直接显示「已申请」标签。

**3.2.9.6.3.4 申请处理（对方侧）**

对方在通知页面看到该申请，通知显示「{申请者姓名} 申请添加你为好友」和申请说明文字。对方点击「同意」后，服务端执行 UPDATE friend_requests SET status='accepted' WHERE id=?，然后执行 INSERT INTO friends (uid, friend_uid) VALUES (当前用户uid, 对方uid) 和 INSERT INTO friends (uid, friend_uid) VALUES (对方uid, 当前用户uid) 建立双向好友关系。对方点击「拒绝」后，服务端执行 UPDATE friend_requests SET status='rejected' WHERE id=?，不写入 friends 表。

### 3.2.9.7 拉黑功能

#### 3.2.9.7.1 拉黑用户

##### 3.2.9.7.1.1 前置条件

用户在成员信息弹窗中查看的成员 uid 不在当前用户的黑名单中。

##### 3.2.9.7.1.2 输入输出规范

| API | 请求体 | 成功响应 | 状态码 |
|-----|--------|---------|--------|
| POST /api/blacklist/add | {uid: string} | {message: '已拉黑'} | 200 |

##### 3.2.9.7.1.3 核心业务处理流程

用户在成员信息弹窗中点击「拉黑」按钮，前端弹出 confirm 对话框，用户确认。前端发送 POST /api/blacklist/add，请求体 {uid: 被拉黑用户uid}。服务端执行 INSERT OR IGNORE INTO blacklist (uid, blocked_uid) VALUES (当前用户uid, 被拉黑用户uid)。服务端返回 {message: '已拉黑'}。前端更新成员信息弹窗中的按钮状态为「取消拉黑」按钮。消息过滤机制生效：loadGroupMessages() 和 loadPrivateMessages() 加载消息时发送 GET /api/blacklist 获取黑名单列表，对返回的消息数组中 sender 在黑名单中的消息不进行渲染。

##### 3.2.9.7.1.4 后置条件

blacklist 表新增一条记录，uid=当前用户uid、blocked_uid=被拉黑用户uid。消息列表中来自被拉黑用户的消息不再显示。

#### 3.2.9.7.2 取消拉黑

##### 3.2.9.7.2.1 前置条件

被拉黑用户 uid 存在于当前用户的黑名单中。

##### 3.2.9.7.2.2 输入输出规范

| API | 请求体 | 成功响应 | 状态码 |
|-----|--------|---------|--------|
| POST /api/blacklist/remove | {uid: string} | {message: '已取消拉黑'} | 200 |

处理流程：用户在成员信息弹窗中点击「取消拉黑」按钮。前端发送 POST /api/blacklist/remove，请求体 {uid: 被拉黑用户uid}。服务端执行 DELETE FROM blacklist WHERE uid=当前用户uid AND blocked_uid=?。服务端返回 {message: '已取消拉黑'}。前端更新成员信息弹窗中的按钮状态为「拉黑」按钮。消息过滤机制停止对该用户的过滤。

### 3.2.9.8 消息发送者名称点击范围

#### 3.2.9.8.1 交互规范

在聊天室消息列表和私聊消息列表中，发送者名称区域（div.sender-name）左键点击时调用 showMemberInfo(this) 函数显示成员信息弹窗。在聊天室消息列表和私聊消息列表中，发送者名称区域（div.sender-name）右键点击时先调用 event.preventDefault() 阻止浏览器默认右键菜单，再调用 showMemberInfo(this) 函数显示成员信息弹窗。在私聊聊天界面中，自己的消息不渲染发送者名称区域，因此不存在点击目标。

## 3.2.10 通知功能（Notification）

### 3.2.10.1 前置条件

用户已完成登录，main.html 左侧导航栏提供「通知」入口，链接至 /notifications 页面。

### 3.2.10.2 输入输出规范

| API | 请求体 | 成功响应 | 状态码 |
|-----|--------|---------|--------|
| GET /api/notifications | 无 | 通知对象数组 | 200 |
| POST /api/notifications/{id}/respond | {type: 'friend_request'|'chat_invite', action: 'accept'|'reject'} | {message} | 200 |

### 3.2.10.3 核心业务处理流程

**3.2.10.3.1 通知数据加载**

通知页面加载时发送 GET /api/notifications 请求。服务端查询 friend_requests 表，筛选 to_uid=当前用户uid AND status='pending' 的记录，每条记录添加 type='friend_request'。服务端查询 chat_invites 表，筛选 invitee_uid=当前用户uid AND status='pending' 的记录，每条记录添加 type='chat_invite'。服务端合并两个查询结果，按 created_at 字段降序排列（最新的通知排在最前面）。

**3.2.10.3.2 好友申请通知处理**

通知条目显示「{申请者姓名} 申请添加你为好友」和申请说明文字（message 字段），下方展示「同意」和「拒绝」按钮。用户点击「同意」后，前端发送 POST /api/notifications/{id}/respond，请求体 {type: 'friend_request', action: 'accept'}。服务端执行 UPDATE friend_requests SET status='accepted' WHERE id=?，然后执行 INSERT INTO friends (uid, friend_uid) VALUES (当前用户uid, 申请者uid) 和 INSERT INTO friends (uid, friend_uid) VALUES (申请者uid, 当前用户uid)。用户点击「拒绝」后，服务端执行 UPDATE friend_requests SET status='rejected' WHERE id=?，不写入 friends 表。

**3.2.10.3.3 聊天室邀请通知处理**

通知条目显示「{邀请者姓名} 邀请你加入聊天室「{聊天室名称}」」和邀请时间，下方展示「同意」和「拒绝」按钮。用户点击「同意」后，前端发送 POST /api/notifications/{id}/respond，请求体 {type: 'chat_invite', action: 'accept'}。服务端执行 UPDATE chat_invites SET status='accepted' WHERE id=?，然后执行 INSERT INTO group_members (group_id, uid, role, joined_at) VALUES (chat_id, 当前用户uid, 'member', now)，最后执行 INSERT INTO group_messages (group_id, sender, content, timestamp, msg_type) VALUES (chat_id, 'system', '{当前用户name} 加入了聊天室', now, 'system')。用户点击「拒绝」后，服务端执行 UPDATE chat_invites SET status='rejected' WHERE id=?，不写入 group_members 表。

**3.2.10.3.4 通知刷新**

通知处理完成后，前端重新发送 GET /api/notifications 获取最新通知列表。已处理的条目不再出现在通知列表中。
