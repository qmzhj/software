3.2.1 用户注册
用户注册功能面向校园统一身份认证体系内的预置用户，仅支持系统预导入的师生账号完成自主注册。用户通过录入个人身份信息、设置合规登录密码完成账号激活，系统可自动识别用户角色并创建专属默认群组，注册完成后账号具备系统登录与基础使用权限。本功能已完成全链路前后端开发，手机号输入模块、身份校验模块、群组创建模块均可正常生效。
3.2.1.1 功能概述
系统仅允许预置在数据库用户表中的校园师生用户执行注册操作，外部陌生账号无法发起注册流程。用户需准确录入学号/工号、真实姓名、手机号，并设置符合复杂度规则的登录密码，完成信息校验后即可激活未注册状态的账号。
注册流程全程包含前端实时校验与后端二次强校验双重机制，可有效拦截非法输入、信息不匹配、重复注册等异常场景。同时系统可根据学工号编码规则自动区分学生、教职工、管理员三类用户角色，注册成功后自动初始化用户所需的系统默认群组。
3.2.1.2 前置条件
系统后台需提前完成基础用户数据初始化工作，所有可注册用户数据均通过固定脚本从users.json文件读取并批量导入系统users数据库表，手动新增外部用户不支持注册。导入的数据包含用户唯一标识uid、用户真实姓名name两大核心基础字段，为身份校验提供数据支撑。
预导入的用户账号具备固定初始状态，users表中registed字段默认赋值为0，代表账号处于未注册未激活状态；账号初始密码为固定123456的SHA-256哈希值，该初始密码仅为数据填充使用，无法用于登录，必须由用户自主注册设置新密码后方可激活使用。
用户操作层面需满足两项基础条件，一是用户必须持有学校备案的有效学号或工号，且知晓系统预置的对应真实姓名，信息需与数据库预存数据完全一致；二是用户使用的终端浏览器已正常加载login.html注册表单界面，页面元素、交互脚本无加载异常。
3.2.1.3 后置条件
用户注册流程执行成功后，数据库users表对应账号的registed字段将由0更新为1，永久标记账号为已注册激活状态，该账号无法重复发起注册请求，实现账号注册唯一性约束。
用户自主设置的登录密码将经过SHA-256哈希加密处理后存入数据库，系统全程不存储任何明文密码，保障用户账号安全。同时用户录入的手机号将同步写入users表新增的phone字段，用于后续密码重置、身份验证等功能，完善用户账号绑定信息。
系统自动为注册用户初始化三类系统默认群组，分别为“即时聊天”“私聊”“课程”群组。其中“即时聊天”“私聊”群组对所有注册用户强制创建，“课程”群组仅在用户存在对应课程数据时自动创建，实现群组资源精准匹配。
账号注册激活完成后，用户可通过已设置的新密码搭配学号/工号，正常登录系统，解锁系统基础使用权限，完成账号从预置未激活状态到可用状态的完整转换。
3.2.1.4 输入输出规范
本功能所有前端输入字段均设置固定格式、长度、必填属性约束，前端表单实时校验字段合规性，后端接口二次校验字段有效性，杜绝非法数据入库。所有输入字段取值、约束规则、业务用途均做唯一化定义，无自定义模糊规则。
接口交互采用标准JSON格式传输数据，区分成功与失败两种响应状态，对应固定HTTP状态码与响应文本，所有异常响应信息精准对应异常场景，便于前端精准展示错误提示。

字段名	标识符	类型	长度	必填	说明
学号/工号	uid	字符串	6-20 字符	是	学校统一身份认证系统中的唯一标识符，用于用户身份唯一校验

成功响应规范：HTTP 状态码固定为201 Created，统一响应体为{"message": "注册成功"}，无自定义返回字段。
失败响应规范：根据异常场景返回对应状态码，参数异常返回400 Bad Request、身份冲突返回409 Conflict、服务异常返回500 Internal Server Error，响应体固定格式为{"error": "<错误描述信息>"}，错误信息与异常场景一一对应。
3.2.1.5 核心业务处理流程
用户注册整体流程遵循「前端输入-前端校验-接口请求-后端多级校验-数据入库-资源初始化-结果反馈」的固定顺序执行，每一步骤均有独立校验逻辑与失败处理机制，流程不可逆、不跳过。
3.2.1.5.1 用户信息录入与角色预判
用户在注册表单对应输入框手动录入注册信息，所有输入框均配置固定HTML标识，系统可精准获取用户录入数据。学号/工号、姓名、手机号、密码、确认密码为核心录入项，各字段均配备标准输入示例，规范用户输入格式。
系统支持实时角色预判功能，用户录入学号/工号时，前端通过正则规则实时匹配账号类型并展示提示信息。录入内容匹配^202\d{9}$规则时，固定展示“系统判定：学生角色”；所有其他合法有效学工号输入，统一展示“系统判定：教职工角色”，提前向用户反馈账号角色属性。

输入框	HTML ID	输入方式	说明
学号/工号	regUid	手动输入	学生学号示例：202421326577，教师工号示例：TE2023001
姓名	regName	手动输入	需与学校备案真实姓名完全一致，区分大小写、无空格容错
手机号	regPhone	手动输入	11位有效中国大陆手机号，为空则不绑定手机，现已适配完整后端逻辑
密码	regPwd	手动输入、密码框隐藏类型	需满足8位及以上长度，包含大小写字母与数字的复杂度规则
确认密码	regConfirm	手动输入、密码框隐藏类型	内容必须与密码输入框内容完全一致，区分字符大小写
3.2.1.5.2 前端密码格式预校验
用户点击注册按钮后，系统优先执行前端本地校验，无需发起网络请求即可拦截不合规密码，减少接口请求压力。校验规则固定为正则表达式^(?=.*[a-z])(?=.*[A-Z])(?=.*\d).{8,}$，全覆盖密码复杂度要求。
该校验规则包含四项强制要求，分别为至少包含1个小写英文字母、至少包含1个大写英文字母、至少包含1位数字、总字符长度不低于8位，四项条件必须同时满足方可通过前端校验。任意条件不满足时，前端立即在regError错误提示区域展示固定提示文案，终止注册流程。
前端校验失败后，系统仅展示错误提示，不会清空用户已录入的表单信息，用户可直接修改密码后重新提交，无需重复填写全部内容，优化用户操作体验。
3.2.1.5.3 前端发起注册接口请求
当前端所有字段校验通过后，前端通过fetch API向固定接口地址POST /api/register发起网络请求，请求数据统一采用JSON格式封装，严格匹配后端接口入参规范，无多余字段、无缺失字段。
请求体固定包含uid、name、password、confirm、phone五个字段，字段取值均为用户表单实时录入内容，请求头默认配置标准application/json格式，保障后端可正常解析请求数据。
3.2.1.5.4 后端基础参数校验
后端接收前端注册请求后，优先执行基础参数校验，校验顺序固定不可调整，依次完成密码格式校验、密码一致性校验，拦截基础输入错误。所有校验失败场景均返回固定HTTP状态码与错误信息。
密码格式校验复用前端统一正则规则，双重保障密码合规性，避免前端校验绕过漏洞；密码一致性校验严格比对password与confirm字段完整内容，字符大小写、长度、内容必须完全一致，任意差异即判定校验失败。
3.2.1.5.5 后端核心身份信息核验
基础参数校验通过后，后端执行核心身份核验逻辑，以用户录入的uid为唯一检索键查询users数据库表，完成三层递进式核验，该逻辑为注册功能核心安全规则，仅预置用户可完成注册。
第一层为账号存在性校验，判断数据库中是否存在对应uid的预置用户数据，无匹配数据则直接拦截注册，杜绝外部账号注册；第二层为姓名匹配校验，比对用户录入姓名与数据库预置name字段内容，必须完全一致方可通过；第三层为注册状态校验，确认账号registed字段为0未注册状态，已注册账号禁止重复注册。
身份核验全程严格匹配校园预置数据，依托学校官方师生信息映射关系，保障注册用户身份真实性，所有核验失败场景均返回409冲突状态码及对应精准错误提示。
3.2.1.5.6 后端自动角色判定
身份核验通过后，系统根据学工号编码正则规则自动判定用户角色，角色分为student学生、teacher教职工、manager管理员三类，匹配优先级固定，可全覆盖系统所有用户类型，同时兼容历史旧数据。
角色判定无需用户手动选择，全程系统自动执行，判定结果将存入用户信息，用于后续权限控制、课程群组匹配、功能权限区分，不同角色用户的系统使用权限与群组资源自动差异化配置。

student（学生）	^202\d{9}$	12位数字、202开头的本科生学号
student（学生）	^[12][0-9]{10}$	11位数字，1开头为博士生学号、2开头为硕士生学号
teacher（教职工）	^TE\d{7}$	TE开头+7位数字的专任教师工号
teacher（教职工）	^T\d{8}$	T开头+8位数字的兼职教师工号
teacher（教职工）	^JG\d{6}$	JG开头+6位数字的学校行政教工工号
teacher（教职工）	^\d{6,8}$	6-8位纯数字格式的老旧教职工工号
manager（管理员）	^ADMIN\d{3}$	ADMIN开头+3位数字的系统管理员账号
manager（管理员）	^MGR\d{4}$	MGR开头+4位数字的系统管理员账号

3.2.1.5.7 密码加密处理
系统统一采用SHA-256哈希加密算法处理用户登录密码，全程不存储明文密码，保障账号数据安全。加密逻辑固定不可逆，所有账号密码加密规则完全统一，避免出现加密规则混乱问题。
加密公式固定为hash = SHA-256(password + SALT)，其中盐值为固定硬编码字符串「CampusFakeSalt2024!」，编码格式统一采用UTF-8，最终加密结果输出为十六进制小写字符串，格式统一无差异。
3.2.1.5.8 用户数据入库更新
所有校验通过后，后端执行固定UPDATE数据库语句更新用户数据，精准更新密码、手机号、注册状态三项核心字段，不修改用户uid、name等预置基础信息，保障原始身份数据不变。
密码字段替换为加密后的SHA-256哈希值，覆盖系统初始默认密码；phone字段赋值为用户录入的手机号，完成手机绑定；registed字段固定更新为1，永久标记账号为已注册状态，锁定注册权限。
3.2.1.5.9 默认群组自动创建
用户数据入库成功后，系统自动调用ensure_default_groups(uid)函数初始化默认群组，所有群组均为system系统类型，分类明确、用途固定，满足用户基础聊天与课程交互需求。
「即时聊天」「私聊」群组为全员强制创建，分别用于临时公共聊天、一对一私密聊天；「课程」群组为条件创建，系统根据用户角色匹配对应课程数据，学生角色查询lesson_stu表选修课程，教师角色查询lesson表授课课程，每门课程自动创建专属课程聊天室。
3.2.1.5.10 注册结果最终反馈
注册成功时，后端返回201状态码与成功提示，前端弹出专属提示框展示“注册成功！请登录”，并自动切换至登录表单页面，引导用户完成登录操作。
注册失败时，前端固定在regError错误提示区域展示后端返回的精准错误信息，保留用户已填写的所有表单数据，支持用户即时修改重试，无需重复录入信息。
3.2.1.6 异常处理机制
系统对注册全流程异常场景做全覆盖处理，明确各类异常的检测时机、HTTP状态码、返回文案，无遗漏异常场景，所有错误提示精准对应问题原因，便于用户修正与运维排查。
前端校验异常、后端参数校验异常、身份核验异常、数据库操作异常、网络异常均有独立处理逻辑，参数类异常统一返回400状态码，身份冲突类异常统一返回409状态码，服务异常统一返回500状态码，层级清晰规范。

3.2.1.7 前端交互规范
注册页面所有表单元素、交互行为、页面切换规则均固定标准化，保证页面交互统一性，避免出现交互逻辑混乱、提示错乱等问题。页面核心元素均配置固定HTML标识，便于脚本精准操控。
注册表单整体ID为registerForm，可通过登录/注册选项卡自由切换，切换瞬间自动清空所有错误提示信息，避免新旧错误信息叠加展示。页面专属配置角色提示区域roleHint、错误提示区域regError，分别用于展示角色预判结果和所有注册异常提示。
注册成功后，前端固定执行三项操作，调用switchTab("login")函数切换至登录表单、清空所有错误提示、开放登录权限，用户可直接使用新密码登录系统。
注册失败后，前端固定保留所有已录入表单数据，仅更新错误提示区域文案，最大程度减少用户重复操作，提升交互体验。
3.2.1.8 数据完整性约束
数据库users表中uid字段设置唯一主键约束，全校范围内无重复学工号，从根源保障用户身份唯一性，杜绝重复账号数据问题。
单个uid账号仅支持一次注册操作，registed字段从0更新为1后永久不可逆转，系统无任何重置注册状态的后台权限，严格保障注册唯一性。
注册阶段所有前端传输数据采用JSON明文传输，当前开发版本未配置传输层加密，生产环境必须部署HTTPS协议，保障数据传输安全。
手机号为非必填字段，支持空字符串入库，未绑定手机号的账号仅无法使用密码重置功能，不影响注册、登录等基础功能使用。
