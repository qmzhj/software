## 赛事发布

赛事数据有两个来源：

1. **预置数据**：`events.json` 在服务启动时自动导入 `events` 表（与 `lessons.json` 导入方式一致）
2. **管理员发布**：赛事列表页给 `role='manager'` 的用户显示"发布赛事"按钮，点击弹出表单填写赛事信息（名称、类型、起止时间、地点、面向对象、主办方、详细介绍），提交 `POST /api/events` 写入 `events` 表

> 旧版 `_seed_data()` 中硬编码的初始数据在引入 `events.json` 后移除，统一由 JSON 导入管理。

`GET /api/events` 返回所有赛事列表，每条包含 `id`、`name`、`type`、`start_time`、`end_time`、`location`、`target`、`organizer`、`description`、`creator_uid`。其中 `id` 用于搜索筛选和详情入口，`creator_uid` 用于聊天室负责人标识。

## 赛事参与

在校园查询页的"赛事活动"标签中，**点击赛事卡片**进入赛事详情界面，内容为:
- 赛事的详细介绍栏目（起止时间、地点、面向对象、主办方、详细介绍）
- 赛事参与人栏目：
    - 用户可在其中创建小组的，寻找队友
    - 用户可设置自己创建的小组的状态为”已满员”
    - 还未加入小组的用户，可申请加入已有的未满员小组
    - 赛事参与人栏目标头中有搜索框，可以输入学号搜索该学号学生所在的小组
    - 赛事参与人栏目标头中有选项：”显示/不显示满员小组”

### 数据模型

增加两张 SQL 表：

```sql
-- 赛事小组表：一个赛事下可创建多个小组
CREATE TABLE events_groups (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    event_id INTEGER NOT NULL,                -- 关联赛事 id
    group_name TEXT NOT NULL,                  -- 小组名称（创建者自定义）
    leader_uid TEXT NOT NULL,                  -- 组长 uid
    status TEXT DEFAULT 'recruiting',          -- 'recruiting' 招募中 | 'full' 已满员
    max_members INTEGER DEFAULT 4,            -- 小组人数上限（默认4人）
    description TEXT,                          -- 小组简介/招募要求
    created_at TEXT DEFAULT (datetime('now', 'localtime')),
    FOREIGN KEY (event_id) REFERENCES events(id),
    FOREIGN KEY (leader_uid) REFERENCES users(uid)
);

-- 小组成员表
CREATE TABLE events_groups_members (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    group_id INTEGER NOT NULL,                 -- 关联小组 id
    member_uid TEXT NOT NULL,                  -- 成员 uid
    joined_at TEXT DEFAULT (datetime('now', 'localtime')),
    FOREIGN KEY (group_id) REFERENCES events_groups(id),
    FOREIGN KEY (member_uid) REFERENCES users(uid),
    UNIQUE(group_id, member_uid)              -- 同一小组内不重复加入
);

```

> **注**：SQLite 默认不启用外键约束（`PRAGMA foreign_keys = OFF`），但应用层已保证数据一致性，故无需额外开启。

### 数据流与操作逻辑

审批流程复用现有的 `notifications` 表，新增通知类型 `'group_join'`：

| notifications 字段 | 存入内容 |
|-------------------|---------|
| `type` | `'group_join'` |
| `sender_uid` | 申请人 uid |
| `receiver_uid` | 组长 uid |
| `content` | 申请留言（可选） |
| `extra` | `{"group_id": <id>, "group_name": "..."}` |
| `status` | `pending` → `approved` / `rejected` |

| 操作 | 后端接口 | 逻辑 |
|------|---------|------|
| 创建小组 | `POST /api/events/<id>/groups` | 创建 `events_groups` 行，组长自动加入 `events_groups_members` |
| 查看小组列表 | `GET /api/events/<id>/groups?show_full=1` | 查询该赛事下的小组，`show_full=0` 时过滤掉 `status='full'` |
| 设置满员 | `PUT /api/events/groups/<gid>/status` | 组长将 `status` 改为 `'full'`，之后不再接受新申请 |
| 搜索成员 | `GET /api/events/groups/search?eid=<id>&uid=<学号>` | 查 `events_groups_members` 联表返回用户所在小组 |
| 申请加入 | `POST /api/events/groups/<gid>/apply` | 创建 `notifications` 行，type=`'group_join'`，`status='pending'` |
| 审批申请 | `POST /api/notifications/<notif_id>/approve` | 组长在通知中心审批。`'group_join'` 分支：插入 `events_groups_members`（**复用现有审批端点，新增 type 分支即可**） |
| 拒绝申请 | `POST /api/notifications/<notif_id>/reject` | 同上，`'group_join'` 分支：更新状态为 `'rejected'` |
| 退出小组 | `DELETE /api/events/groups/<gid>/members/<uid>` | 普通成员退出（组长需先转让或解散） |

### 与现有 API 的兼容性检查

| 建议路由 | 现有路由冲突 | 说明 |
|---------|------------|------|
| `POST /api/events/<id>/groups` | 无 | `events` 端点只有 `GET /api/events` |
| `GET /api/events/<id>/groups` | 无 | 同上 |
| `PUT /api/events/groups/<gid>/status` | 无 | 无冲突 |
| `GET /api/events/groups/search` | 无 | 无冲突 |
| `POST /api/events/groups/<gid>/apply` | 无 | 无冲突 |
| `DELETE /api/events/groups/<gid>/members/<uid>` | 无 | 无冲突 |
| `POST /api/notifications/<id>/approve` | 已有 | **复用**，新增 `'group_join'` type 分支 |
| `POST /api/notifications/<id>/reject` | 已有 | **复用**，新增 `'group_join'` type 分支 |

所有新路由均不存在冲突，审批流程无缝接入现有的通知审批机制。

### 与赛事详情界面的关系

赛事详情界面中，"赛事参与人"栏目展示该赛事下的所有小组，每个小组卡片包含：
- 小组名、组长名、成员数/上限、状态徽标（招募中/已满员）
- 若当前用户未加入任何小组 → 显示"申请加入"按钮
- 若当前用户是组长 → 显示"设置满员"按钮

界面右侧/顶部的搜索框支持按学号搜索用户所在小组，切换开关控制是否显示已满员小组。


# 用户搜索
用户可通过学号/姓名、课程、班级、身份、赛事五个筛选条件搜索其它用户，多个条件可组合使用（AND 查询）。

## 身份系统设计

### 数据模型

```sql
-- 班级表
CREATE TABLE classes (
    class_id TEXT PRIMARY KEY, -- 直接用 class_name 作为 class_id（班级名唯一，无需 hash）
    class_name TEXT,       -- 如"网工一班"
    grade TEXT,            -- 2024
    major TEXT,            -- 网络工程
    department TEXT,       -- 计算机学院
    level TEXT DEFAULT 'class'  -- 'class' 班级群 | 'grade' 年级群
);

-- 班干部职位（附加标记，不影响 users.role）
CREATE TABLE class_positions (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    class_id TEXT NOT NULL,
    uid TEXT NOT NULL,
    position_name TEXT NOT NULL,  -- '班长'|'团支书'|'学委'|'组委'|'心委'|'兼班'|'兼助'|...
    FOREIGN KEY (class_id) REFERENCES classes(class_id),
    FOREIGN KEY (uid) REFERENCES users(uid)
);

-- 课程职位表（关联课程而非班级），与 class_positions 结构一致
-- 数据由教师在课程聊天室中自行设置，不从 JSON 加载
CREATE TABLE lesson_positions (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    lesson_id TEXT NOT NULL,
    uid TEXT NOT NULL,
    position_name TEXT NOT NULL,  -- '课代表'|'助教'|...
    FOREIGN KEY (lesson_id) REFERENCES lesson(lesson_id),
    FOREIGN KEY (uid) REFERENCES users(uid)
);

-- 班级成员关联表（class_id → 学生uid），与 lesson_stu 命名一致
CREATE TABLE class_stu (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    class_id TEXT NOT NULL,
    uid TEXT NOT NULL,
    FOREIGN KEY (class_id) REFERENCES classes(class_id),
    FOREIGN KEY (uid) REFERENCES users(uid)
);
```
其中班级数据从class.json文件读取（服务启动时自动导入，与lessons.json的导入方式一致），参考`自动创建课程群组要求.md`中lessons.json的数据格式设计，json文件中数据格式为


### JSON→数据库映射说明

JSON 中的 `class_cadre` 数据导入时写入 `class_positions` 表，映射关系：
```
class_cadre: {"班长": "202421326578", "团支书": "202421326579"}
  → class_positions: (class_id='网工一班', uid='202421326578', position_name='班长')
                      (class_id='网工一班', uid='202421326579', position_name='团支书')
```
`class_member` 数组导入 `class_stu` 表，每条为 `(class_id, uid)` 映射。

### 设计思路

- **`users.role`（student/teacher/manager）不变**，班干部和课代表只是附加标记，不走权限继承
- 职位类型用字符串存，新增职位直接加数据，不改表结构
- 课代表关联的是课程（`lesson_id`）而非班级，与班干部职责域天然分开

### 搜索实现

#### 搜索入口

改造现有搜索框，不再使用下拉菜单选模式。改为五个筛选框横向一字排开，课程/班级/身份/赛事采用**输入+自动补全**控件。用户可以在任意筛选框中填写条件，留空的筛选框不参与过滤。

```
[学号/姓名:_________] [课程:输入+▼] [班级:输入+▼] [身份:输入+▼] [赛事:输入+▼]  [搜索]
```

- **学号/姓名**：文本输入框，支持模糊匹配
- **课程**：输入+自动补全，数据源 `GET /api/search/options?type=courses`
- **班级**：输入+自动补全，数据源 `GET /api/search/options?type=classes`
- **身份**：输入+自动补全，预设固定列表（班长/团支书/学习委员/副级长/年级团总支/辅导员/课代表/兼班/兼助）
- **赛事**：输入+自动补全，数据源 `GET /api/events`

前端提交时，将非空的筛选条件以查询参数传给后端：

```
GET /api/search/users?name_or_id=张三&class=网工一班&position=班长
GET /api/search/users?class=网工一班
GET /api/search/users?course=软件工程
GET /api/search/users?event_id=1
GET /api/search/users?name_or_id=202421324906
```

后端将所有非空参数做 **AND 查询**（多个条件同时满足才返回），实现路径：

| 查询参数 | 说明 | SQL/查询逻辑 |
|---------|------|-------------|
| `name_or_id` | 学号或姓名 | `users.uid` 或 `users.name` LIKE 模糊匹配 |
| `course` | 课程名 | 通过 `lesson_stu` / `lesson` 找到上该课程的用户 |
| `class` | 班级名 | 通过 `class_stu` 找到该班级的用户 |
| `position` | 职位名 | 通过 `class_positions` / `lesson_positions` 找到有该职位的用户 |
| `event_id` | 赛事 ID | 通过 `events_groups` → `events_groups_members` 找到参与该赛事的用户 |

#### 返回格式

搜索结果返回用户列表时，附带身份标签：

```json
[
    {
        "uid": "202421326578",
        "name": "张三",
        "role": "student",
        "tags": ["班长", "课代表-数据结构"]
    }
]
```

- `tags` 数组，包含该用户在所有班级/课程中的职位，以及参与的赛事标签
- 参与赛事的用户额外添加标签 `"参赛-{赛事名}"`（如 `"参赛-ROBOTAC 机器人挑战赛"`）
- 前端以徽标（badge）形式在每个用户旁展示身份标签
- **标签按所填筛选条件追加展示**，填了哪类条件就追加展示该类标签，不填则不展示：

| 填写的筛选条件 | 前端展示的标签 |
|--------------|--------------|
| 仅填学号/姓名 | 不展示任何标签（默认干净视图） |
| 填了课程 | 追加展示该课程的课代表/助教标签 |
| 填了班级 | 追加展示该班级的班干部标签 |
| 填了身份 | 追加展示匹配的职位标签 |
| 填了赛事 | 追加展示参赛标签（`参赛-{赛事名}`） |
| 同时填了多个 | 同时展示各类标签（如填"班级+课程"则班干部和课代表标签都展示） |

> **标签筛选规则**：每填一个筛选条件，就追加展示该类别下的标签，未填类别不展示。例如仅填"班级"只看到班干部标签，同时填"班级+课程"则班干部和课代表标签都展示。不填任何条件（仅学号/姓名）时完全不展示标签。

### 为什么这个方案够用

- 五个筛选框横向排列，充分利用页面宽度
- 支持多条件组合，不用单独搞一个"组合搜索"模式
- 后端 AND 查询简单直接，前端渲染逻辑清晰
- 可演示性足够：选"网工一班"+ 选"班长"能正确返回林枫灿并显示标签

### 聊天室详情界面设计

根据聊天室类型，详情界面采用不同的成员展示和操作逻辑。后端通过 `creator` 和 `category` 区分类型：

| 聊天室类型 | `creator` | `category` | 识别方式 |
|-----------|----------|-----------|---------|
| 普通聊天室 | 用户 uid | 自定义 | 用户创建，自定义分类 |
| 课程聊天室 | `system` | `课程` | 自动创建，关联课程 |
| 班级聊天室 | `system` | `班级` | 自动创建，关联班级 |
| 赛事聊天室 | `system` | `赛事` | 赛事发布时自动创建 |

#### 普通聊天室

- 成员平铺展示
- 身份标识：`🔑群主`（`role='admin'`）、`🛡️管理员`（`role='manager'`）
- 不显示职位标签
- 群主可操作：**设为管理员** / **取消管理** / **踢出**

#### 课程聊天室

- 成员平铺展示，不分区
- 群主（教师）显示 `👑教师` 替代 `🔑群主`，管理员显示 `🛡️管理员`
- 职位标签（仅限课程相关）：`📖课代表`（`lesson_positions`）
- 教师和课代表显示在成员列表顶部
- 管理员操作栏中，以 **"设为课代表"** 按钮替换 **"设为管理员"** 按钮
- 不显示班级/年级等非课程职位标签

#### 班级聊天室

- 成员列表分两个栏目展示：班干部栏 + 班级成员栏
- 班干部显示具体职位名称（班长/团支书/兼班/兼助...）及 `🔑群主` 标识
- 仅显示该班级自己的职位标签，不展示年级级或其他班级标签
- 不显示"设为管理员"或"设为课代表"按钮

#### 赛事聊天室

- 与普通聊天室渲染逻辑相同，成员平铺展示
- 身份标识：`🏆负责人`（替代 `🔑群主`）、`🛡️管理员`
- 不显示职位标签

## 现有课程相关表说明

系统中已有的两张课程表，与身份系统配合使用：

### lesson（课程表）

```sql
CREATE TABLE IF NOT EXISTS lesson (
    lesson_id TEXT PRIMARY KEY,      -- 自动生成 hash
    lesson_name TEXT,                -- 课程名
    teacher_uid TEXT,                -- 授课教师 uid
    schedule_weekday TEXT,           -- 星期几
    schedule_period TEXT,            -- 第几节（如 "1-2"）
    schedule_weeks TEXT,             -- 上课周数（如 "1-16"）
    location TEXT                    -- 上课地点
);
```

### lesson_stu（课程-学生关联表）

```sql
CREATE TABLE IF NOT EXISTS lesson_stu (
    lesson_id TEXT,
    stu_uid TEXT,
    PRIMARY KEY(lesson_id, stu_uid)
);
```

### 数据来源

从 `lessons.json` 读取，格式如下：

```json
{
    "lesson_name": "数据结构",
    "teacher_uid": "202421326500",
    "schedule_weekday": "星期三",
    "schedule_period": "1-2",
    "schedule_weeks": "1-16",
    "location": "北504",
    "stu_uids": ["202421326577", "202421326578", ...]
}
```

### 与身份系统的关系

- 课程聊天室由 `_create_course_chat_rooms()` 在初始化时创建，`ensure_default_groups()` 负责关联到"课程和班级"群组
- `lesson.teacher_uid` 的教师自动设为聊天室管理员（`group_members.role='admin'`）
- `lesson_positions` 扩展存储课代表/助教等课程职位，课代表 `group_members.role` 保持 `'member'`
