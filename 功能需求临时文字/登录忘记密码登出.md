# 用户登录、忘记密码与登出功能需求规格说明

## 3.2 用户认证

### 3.2.1 功能概述

本功能涵盖三个子功能：
- **登录（3.2.2）**：已注册用户通过学号/工号和密码进行身份认证，获取会话 Token 并进入系统主界面。
- **忘记密码（3.2.3）**：已注册用户通过手机短信验证码重置登录密码。
- **登出（3.2.4）**：已登录用户主动结束当前会话，清除本地登录凭证。

#### 前置条件（所有子功能通用）

1. 存在 `users` 表，且至少已导入预置用户数据（详见注册功能）。
2. 登录和忘记密码的前端表单已在 [login.html](../static/login.html) 中正常渲染。

---

### 3.2.2 登录

#### 3.2.2.1 输入输出规范

**API 接口：**

| 项目 | 值 |
|------|-----|
| 接口 URL | `/api/login` |
| HTTP 方法 | `POST` |
| 请求 Content-Type | `application/json` |
| 认证要求 | 无（无需 Token） |

**输入字段：**

| 字段名 | 标识符 | 类型 | 必填 | 说明 |
|--------|--------|------|------|------|
| 学号/工号 | `uid` | 字符串 | 是 | 用户在系统中注册的学号或工号 |
| 密码 | `password` | 字符串 | 是 | 用户注册时设置的登录密码 |

**请求示例：**
```json
{"uid": "202421326577", "password": "Abc123456"}
```

**成功响应：**
- HTTP 状态码：`200 OK`
- 响应体：`{"message": "登录成功", "token": "<32位十六进制字符串>", "name": "<用户姓名>", "role": "<用户角色>"}`

#### 3.2.2.2 登录流程

##### 步骤 1 — 用户输入凭证

用户在登录表单（`loginForm`）中输入学号/工号和密码，点击"登录"按钮。

| 输入框 | HTML ID | 说明 |
|--------|---------|------|
| 学号/工号 | `loginUid` | 用户在系统中的唯一标识符 |
| 密码 | `loginPwd` | 密码框类型输入 |
| 错误提示区域 | `loginError` | 用于显示登录失败的错误信息 |

##### 步骤 2 — 前端发送登录请求

前端通过 `fetch` API 向 `POST /api/login` 发送 JSON 请求。

##### 步骤 3 — 后端查找用户

以 `uid` 为键查询 `users` 表。

**用户不存在：** 若 `users` 表中无匹配记录，返回 `404 {"error": "账号不存在"}`，流程结束。

##### 步骤 4 — 检查注册状态

检查 `users` 表中该用户的 `registed` 字段值。

**账号未注册：** 若 `registed = 0`，说明用户尚未完成注册流程，返回 `404 {"error": "账号未注册"}`，流程结束。

##### 步骤 5 — 检查账号锁定状态

检查 `users` 表中该用户的 `locked` 字段值。

**锁定逻辑：**

| 条件 | 处理方式 | 响应 |
|------|----------|------|
| `locked = 0` | 账号正常，继续执行步骤 6 | — |
| `locked = 1` 且 `当前时间 < unlock_time` | 账号仍处于锁定期 | `403 {"error": "账户已锁定，请于{YYYY-MM-DD HH:MM}后重试"}`，流程结束 |
| `locked = 1` 且 `当前时间 >= unlock_time` | 锁定已到期，解除锁定：设置 `locked=0`、`login_fails=0`，继续执行步骤 6 | — |

##### 步骤 6 — 密码验证

对用户输入的密码使用与注册相同的加密算法（SHA-256 + 固定盐值 `CampusFakeSalt2024!`）计算哈希值，与 `users` 表中存储的 `password` 字段进行比对。

**密码匹配：** 执行以下操作：
1. 生成会话 Token：`secrets.token_hex(16)`（32 字符随机十六进制字符串）
2. 将 `{token: uid}` 存入内存字典 `tokens`（Token 到用户 ID 的映射）
3. 重置登录失败计数：`UPDATE users SET login_fails=0, locked=0 WHERE uid=?`
4. 调用 `ensure_default_groups(uid)`，确保用户已拥有默认系统群组（"即时聊天"、"私聊"、"课程"）
5. 返回 `200 {"message": "登录成功", "token": token, "name": name, "role": role}`

**密码不匹配：** 执行以下操作：
1. 累加登录失败次数：`login_fails = login_fails + 1`
2. 判断是否达到锁定阈值：
   - 若 `login_fails >= 5`：锁定账号，记录解锁时间（当前时间 + 30 分钟），返回 `403 {"error": "账户已锁定，请30分钟后重试"}`
   - 若 `login_fails < 5`：更新失败次数，返回 `401 {"error": "密码错误，还可尝试{5-fails}次"}`

##### 步骤 7 — 前端处理登录结果

**登录成功：**
1. 将以下信息存入 `localStorage`：

| localStorage Key | 值来源 | 说明 |
|-----------------|--------|------|
| `token` | 响应中的 `token` | 后续请求的身份凭证 |
| `name` | 响应中的 `name` | 用户姓名，用于界面显示 |
| `role` | 响应中的 `role` | 用户角色，用于权限控制 |
| `uid` | 用户输入的学号/工号 | 用户标识 |

2. 跳转至主界面：`window.location.href = "/main"`

**登录失败：** 在错误提示区域（`loginError`）展示后端返回的具体错误信息。

### 3.2.3 忘记密码（密码重置）

#### 3.2.3.1 功能概述

允许已注册用户通过绑定的手机号接收验证码，验证通过后重置登录密码。本功能分为两个步骤：发送验证码和重置密码。

#### 3.2.3.2 短信验证码管理

- 验证码存储于内存字典 `verification_codes`，键为手机号
- 每个验证码的有效期为 5 分钟（自生成时起算）
- 验证码验证最多允许 5 次尝试，超过后自动清除
- **开发阶段验证码固定为 `"123456"`（未对接真实短信通道）**
- 系统在每次发送新验证码前会清理所有已过期的验证码记录

#### 3.2.3.3 步骤一：发送验证码

##### 输入输出规范

**API 接口：**

| 项目 | 值 |
|------|-----|
| 接口 URL | `/api/change_password` |
| HTTP 方法 | `POST` |
| 请求 Content-Type | `application/json` |
| 认证要求 | 无 |

**请求体：**

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `action` | 字符串 | 是 | 固定值 `"send_code"` |
| `uid` | 字符串 | 是 | 学号/工号 |
| `phone` | 字符串 | 是 | 用户绑定的手机号 |

**请求示例：**
```json
{"action": "send_code", "uid": "202421326577", "phone": "13800138000"}
```

##### 发送流程

| 步骤 | 验证项 | 验证逻辑 | 失败响应 |
|------|--------|----------|----------|
| 1 | 手机号非空检查 | `phone` 字段不为空 | `400 {"error": "手机号不能为空"}` |
| 2 | 手机号格式验证 | 以 `1` 开头，长度 11 位，全数字 | `400 {"error": "手机号格式不正确"}` |
| 3 | 学工号存在性检查 | `users` 表中存在该 `uid` | `404 {"error": "该账号不存在"}` |
| 4 | 手机号匹配检查 | 该用户 `users.phone` 与输入的 `phone` 一致 | `404 {"error": "学号/工号与手机号不匹配"}` |

**全部验证通过后：**
1. 生成验证码（当前硬编码为 `"123456"`）
2. 调用短信发送函数 `send_sms(phone, code)`（当前为空函数，始终返回 `True`）
3. 验证码存入内存：`verification_codes[phone] = {code, expires_at: time()+300, attempts: 0}`
4. 返回 `200 {"success": true, "message": "验证码已发送"}`

#### 3.2.3.4 步骤二：重置密码

##### 输入输出规范

| 项目 | 值 |
|------|-----|
| 接口 URL | `/api/change_password` |
| HTTP 方法 | `POST` |
| 请求 Content-Type | `application/json` |
| 认证要求 | 无 |

**请求体：**

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `action` | 字符串 | 是 | 固定值 `"reset_password"` |
| `uid` | 字符串 | 是 | 学号/工号 |
| `phone` | 字符串 | 是 | 用户绑定的手机号 |
| `code` | 字符串 | 是 | 短信验证码 |
| `new_password` | 字符串 | 是 | 新密码（需满足密码复杂度规则） |

**请求示例：**
```json
{
  "action": "reset_password",
  "uid": "202421326577",
  "phone": "13800138000",
  "code": "123456",
  "new_password": "NewPwd789"
}
```

##### 重置流程

| 顺序 | 验证项 | 验证逻辑 | 失败响应 |
|------|--------|----------|----------|
| 1 | 字段完整性检查 | `phone`、`code`、`new_password`、`uid` 均非空 | `400 {"error": "请填写完整信息"}` |
| 2 | 新密码格式验证 | 同注册密码规则：`^(?=.*[a-z])(?=.*[A-Z])(?=.*\d).{8,}$` | `400 {"error": "密码需包含大小写字母和数字，至少8位"}` |
| 3 | 验证码存在性检查 | `phone` 存在于 `verification_codes` 中 | `400 {"error": "验证码已过期，请重新获取"}` |
| 4 | 验证码有效期检查 | `time.now() <= verification_codes[phone].expires_at`（5分钟超时） | `400 {"error": "验证码已过期，请重新获取"}` |
| 5 | 验证码正确性检查 | 输入的 `code` 与存储值一致 | `400 {"error": "验证码不正确"}`（尝试次数 +1，5 次失败后清除验证码并提示"验证失败次数过多，请重新获取验证码"） |
| 6 | 学工号-手机号匹配 | `users` 表中该 `uid` 对应的 `phone` 与输入值一致 | `404 {"error": "学号/工号与手机号不匹配"}` |

**全部验证通过后：**
1. 对新密码进行 SHA-256 哈希计算（盐值同注册功能）
2. 执行 `UPDATE users SET password = <哈希值> WHERE uid = <学号/工号>`
3. 清除已使用的验证码（从 `verification_codes` 中删除）
4. 返回 `200 {"success": true, "message": "密码修改成功"}`

##### 前端处理

- 发送验证码后启动 60 秒倒计时，按钮禁用并显示"重新发送(XXs)"
- 重置成功后显示"密码修改成功，请返回登录"，3 秒后自动跳转回登录表单

### 3.2.4 登出

#### 3.2.4.1 输入输出规范

**API 接口：**

| 项目 | 值 |
|------|-----|
| 接口 URL | `/api/logout` |
| HTTP 方法 | `POST` |
| 请求 Header | `Authorization: <token>` |
| 认证要求 | 需要有效的 Bearer Token |

**成功响应：** `200 OK`，`{"message": "已登出"}`

**失败响应：** `401 {"error": "登录已过期"}`（Token 无效或已过期）

#### 3.2.4.2 登出流程

##### 步骤 1 — 用户触发登出

用户在主界面左侧导航栏点击"退出登录"按钮（`.logout` 类）。

##### 步骤 2 — 前端发送登出请求

前端通过 `fetch` 向 `POST /api/logout` 发送请求，携带 `Authorization` 请求头，值为 `localStorage` 中存储的 Token。

##### 步骤 3 — 后端处理（Token 鉴权 + 清除）

`@token_required` 装饰器执行 Token 验证：
1. 从 `Authorization` 请求头中提取 Token
2. 在内存 `tokens` 字典中查找该 Token
3. 若 Token 不存在或无效，返回 `401 {"error": "登录已过期"}`
4. 若 Token 有效，将当前用户信息注入 `g.current_user`

验证通过后：
1. 从内存 `tokens` 字典中删除该 Token 条目
2. 返回 `200 {"message": "已登出"}`

##### 步骤 4 — 前端处理（无关后端响应）

无论后端请求成功或失败（使用 `.finally()`），前端执行：
1. `localStorage.clear()` — 清除所有本地存储数据（Token、姓名、角色、学号等）
2. `location.href = "/"` — 跳转回登录页面

### 3.2.5 异常/备选流程

#### 3.2.5.1 登录异常

| 异常场景 | 检测时机 | HTTP 状态码 | 返回信息 |
|----------|----------|-------------|----------|
| 账号不存在 | 3.2.2.2 步骤 3 | 404 | `账号不存在` |
| 账号未注册 | 3.2.2.2 步骤 4 | 404 | `账号未注册` |
| 账号已锁定（锁定期内） | 3.2.2.2 步骤 5 | 403 | `账户已锁定，请于{YYYY-MM-DD HH:MM}后重试` |
| 密码错误（未达锁定阈值） | 3.2.2.2 步骤 6 | 401 | `密码错误，还可尝试{N}次` |
| 密码错误（已达锁定阈值 5 次） | 3.2.2.2 步骤 6 | 403 | `账户已锁定，请30分钟后重试` |
| 数据库异常 | 后端任意步骤 | 500 | `系统繁忙` |
| 网络连接失败 | 前端请求 | N/A | `网络错误` |

#### 3.2.5.2 忘记密码异常

| 异常场景 | 触发步骤 | HTTP 状态码 | 返回信息 |
|----------|----------|-------------|----------|
| 手机号为空 | 3.2.3.3 发送步骤 1 | 400 | `手机号不能为空` |
| 手机号格式不正确 | 3.2.3.3 发送步骤 2 | 400 | `手机号格式不正确` |
| 学工号不存在 | 3.2.3.3 发送步骤 3 | 404 | `该账号不存在` |
| 学工号与手机号不匹配 | 3.2.3.3 发送步骤 4 | 404 | `学号/工号与手机号不匹配` |
| 验证码已过期 | 3.2.3.4 重置步骤 3/4 | 400 | `验证码已过期，请重新获取` |
| 验证码不正确 | 3.2.3.4 重置步骤 5 | 400 | `验证码不正确` |
| 验证错误超过 5 次 | 3.2.3.4 重置步骤 5 | 400 | `验证失败次数过多，请重新获取验证码` |
| 学工号与手机号不匹配（重置时） | 3.2.3.4 重置步骤 6 | 404 | `学号/工号与手机号不匹配` |
| 密码格式不合法 | 3.2.3.4 重置步骤 2 | 400 | `密码需包含大小写字母和数字，至少8位` |

#### 3.2.5.3 登出异常

| 异常场景 | 检测时机 | HTTP 状态码 | 返回信息 |
|----------|----------|-------------|----------|
| 未提供 Token 或 Token 无效 | 后端 Token 验证 | 401 | `登录已过期` |
| Token 在服务端已失效（如已被其他设备登出） | 后端 Token 查找 | 401 | `登录已过期` |

**注意：** 前端登出处理使用了 `.finally()`，因此即使用户本地 Token 已失效（如已被其他设备登出），前端仍会清除 `localStorage` 并跳转回登录页。

### 3.2.6 账号锁定机制详细规则

锁定机制用于防御暴力破解，规则如下：

| 规则项 | 值 |
|--------|-----|
| 锁定阈值 | 连续 5 次密码错误 |
| 锁定持续时间 | 30 分钟 |
| 锁定计数归属 | 按 `uid` 独立计数（`users.login_fails`） |
| 解锁方式 | 自动解锁（到期后首次登录尝试时解除） |
| 成功登录后 | 重置 `login_fails = 0`、`locked = 0` |

---

### 3.2.7 数据完整性约束

1. Token 存储在服务器内存中（`tokens` 字典），服务重启后所有 Token 失效，已登录用户需重新登录。
2. 同一用户可以同时拥有多个有效 Token（多设备登录），每个 Token 对应一个独立会话。
3. `users.uid` 在表中是主键，具有唯一性约束。
4. 密码在数据库中以 SHA-256 哈希形式存储，不存储明文密码。
5. 验证码以明文形式存储在内存中（非持久化），服务重启后所有验证码失效。

---

### 3.2.8 安全性说明

| 安全措施 | 说明 |
|----------|------|
| 密码哈希存储 | 使用 SHA-256 + 固定盐值，防止密码明文泄露 |
| 登录失败锁定 | 连续 5 次失败锁定 30 分钟，防御暴力破解 |
| Token 随机生成 | 使用 `secrets.token_hex(16)` 生成密码学安全的随机 Token |
| 验证码有效期 | 5 分钟过期 + 最多 5 次验证尝试 |

**当前局限（开发阶段）：**
- Token 存储在内存中，服务重启后全部失效
- 未使用 HTTPS（密码在传输层为明文 JSON）
- 短信验证码硬编码为 `"123456"`，未对接真实短信通道
- 盐值为固定值硬编码在代码中（生产环境应使用随机盐值 + 逐用户盐）
