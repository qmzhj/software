# 用户注册功能需求规格说明

## 1. 功能概述

允许已在校园统一身份认证系统中登记的用户（预置在 `users.json` 中），通过验证学号/工号、姓名和手机号完成账号注册，设置登录密码，激活账号。注册成功后系统自动为用户创建默认群组。

## 2. 前置条件

1. 用户数据已由系统管理员预导入 `users` 表（数据源为 `users.json`，包含 `uid`、`name` 字段）。
2. 预导入用户的初始状态为：`registed = 0`（未注册）、默认密码为 `123456` 的 SHA-256 哈希值。
3. 用户必须持有有效的学号/工号及与之对应的真实姓名。
4. 浏览器已加载 [login.html](../static/login.html) 注册表单界面。

## 3. 后置条件

1. 用户账号被激活（`users.registed` 置为 `1`）。
2. 用户设置的密码经 SHA-256 哈希处理后存入数据库，明文密码不被存储。
3. 系统为该用户自动创建三个系统群组："即时聊天"、"私聊"、"课程"（若用户有课程数据）。
4. 用户可使用学号/工号和新设密码登录系统。

## 4. 输入输出规范

### 4.1 输入字段

| 字段名 | 标识符 | 类型 | 长度 | 必填 | 说明 |
|--------|--------|------|------|------|------|
| 学号/工号 | `uid` | 字符串 | 6-20 字符 | 是 | 学校统一身份认证系统中的唯一标识符 |
| 姓名 | `name` | 字符串 | 1-50 字符 | 是 | 用户在学校的现用真实姓名 |
| 密码 | `password` | 字符串 | 8-128 字符 | 是 | 登录密码，需满足密码复杂度规则 |
| 确认密码 | `confirm` | 字符串 | 8-128 字符 | 是 | 密码确认字段，必须与 `password` 值一致 |
| 手机号 | `phone` | 字符串 | 11 字符 | 否 | 用户手机号，可用于密码找回 |

### 4.2 输出规范

**成功响应：**
- HTTP 状态码：`201 Created`
- 响应体：`{"message": "注册成功"}`

**失败响应：**
- HTTP 状态码：`400 Bad Request`、`409 Conflict`、`500 Internal Server Error`
- 响应体：`{"error": "<错误描述信息>"}`

### 4.3 API 接口定义

| 项目 | 值 |
|------|-----|
| 接口 URL | `/api/register` |
| HTTP 方法 | `POST` |
| 请求 Content-Type | `application/json` |
| 认证要求 | 无（无需 Token） |

## 5. 功能流程

### 5.1 步骤 1 — 用户输入注册信息（前端）

用户在注册表单中填写以下信息：

| 输入框 | HTML ID | 输入方式 | 说明 |
|--------|---------|----------|------|
| 学号/工号 | `regUid` | 手动输入 | 示例：`202421326577`（学生学号）或 `TE2023001`（教师工号） |
| 姓名 | `regName` | 手动输入 | 示例：`张三` |
| 手机号 | `regPhone` | 手动输入 | 示例：`13800138000` |
| 密码 | `regPwd` | 手动输入，密码框类型 | 至少 8 位，需包含大小写字母和数字 |
| 确认密码 | `regConfirm` | 手动输入，密码框类型 | 必须与密码输入一致 |

**辅助提示：** 系统在用户输入学号/工号时实时显示角色预判提示：
- 学号匹配 `^202\d{9}$` 模式时，显示"系统判定：学生角色"
- 其他有效输入显示"系统判定：教职工角色"

### 5.2 步骤 2 — 前端密码格式验证

用户点击"注册"按钮后，前端发送请求前，由浏览器端 JavaScript 对密码格式进行验证。

**密码复杂度规则（正则表达式）：**

```
^(?=.*[a-z])(?=.*[A-Z])(?=.*\d).{8,}$
```

- `(?=.*[a-z])` — 至少包含 1 个小写英文字母
- `(?=.*[A-Z])` — 至少包含 1 个大写英文字母
- `(?=.*\d)` — 至少包含 1 个数字
- `.{8,}` — 总长度至少为 8 个字符

**验证失败处理：** 若密码不符合上述规则，前端立即在注册表单错误提示区域（`regError`）显示错误信息"密码需包含大小写字母和数字，至少8位"，不发送网络请求。

### 5.3 步骤 3 — 前端向后端发送注册请求

前端通过 `fetch` API 向 `POST /api/register` 发送 JSON 格式请求体：

```json
{
  "uid": "202421326577",
  "name": "曹云龙",
  "password": "Abc123456",
  "confirm": "Abc123456",
  "phone": "13800138000"
}
```

### 5.4 步骤 4 — 后端接收与初步验证

后端接收请求后执行以下验证（按顺序）：

| 顺序 | 验证项 | 验证逻辑 | 失败响应 |
|------|--------|----------|----------|
| 4.1 | 密码格式验证 | 使用正则 `^(?=.*[a-z])(?=.*[A-Z])(?=.*\d).{8,}$` 校验 `password` 字段 | 400 `{"error": "密码需包含大小写字母和数字，至少8位"}` |
| 4.2 | 密码一致性验证 | 比较 `password` 与 `confirm` 的值是否完全一致 | 400 `{"error": "两次密码不一致"}` |

### 5.5 步骤 5 — 后端用户信息核验（关键步骤）

以 `uid` 为键查询 `users` 表，按顺序执行以下核验：

| 顺序 | 核验项 | 核验逻辑 | 失败响应 |
|------|--------|----------|----------|
| 5.1 | 学号/工号存在性检查 | 查询 `users` 表中是否存在该 `uid` 的记录 | 409 `{"error": "无该学工号"}` |
| 5.2 | 姓名匹配检查 | 比较输入的 `name` 与 `users` 表中该 `uid` 对应的 `name` 字段值是否一致 | 409 `{"error": "学工号与姓名不匹配!"}` |
| 5.3 | 注册状态检查 | 检查 `users` 表中该 `uid` 的 `registed` 字段是否为 `0`（未注册） | 409 `{"error": "该用户已注册!"}` |

**业务规则说明：**
- 只有预置在 `users` 表中的用户才能注册（即：用户数据必须先由系统从 `users.json` 导入数据库）。
- 姓名必须与预置数据完全一致（区分大小写，不含空格容错）。
- 已注册用户（`registed = 1`）不可重复注册。

### 5.6 步骤 6 — 后端自动判断用户角色

系统根据学号/工号的编码规则自动判断角色，角色赋值逻辑按以下优先级执行：

| 角色 | 匹配模式（正则表达式） | 适用对象 |
|------|----------------------|----------|
| `student`（学生） | `^202\d{9}$` | 本科生，12 位数字，以 `202` 开头 |
| `student`（学生） | `^[12][0-9]{10}$` | 研究生，11 位数字，以 `1`（博士）或 `2`（硕士）开头 |
| `teacher`（教师） | `^TE\d{7}$` | 专任教师，以 `TE` 开头 + 7 位数字 |
| `teacher`（教师） | `^T\d{8}$` | 兼职教师，以 `T` 开头 + 8 位数字 |
| `teacher`（教师） | `^JG\d{6}$` | 教工，以 `JG` 开头 + 6 位数字 |
| `teacher`（教师） | `^\d{6,8}$` | 纯数字工号 |
| `manager`（管理员） | `^ADMIN\d{3}$` | 管理员，以 `ADMIN` 开头 + 3 位数字 |
| `manager`（管理员） | `^MGR\d{4}$` | 管理员，以 `MGR` 开头 + 4 位数字 |
| `manager`（管理员） | `^admin$` / `^administrator$`（不区分大小写） | 系统管理员账号 |
| `teacher`（教师） | 默认（不匹配上述所有规则） | 兼容旧数据 |

### 5.7 步骤 7 — 密码加密处理

使用固定盐值对密码进行 SHA-256 哈希计算，**明文密码不存入数据库**。

**加密算法：**

```
hash = SHA-256(password + SALT)
```

- 哈希算法：`SHA-256`（`hashlib.sha256`）
- 固定盐值：`"CampusFakeSalt2024!"`（字符串常量，硬编码于后端代码）
- 编码方式：UTF-8
- 输出格式：十六进制小写字符串

### 5.8 步骤 8 — 用户信息写入数据库

执行 `UPDATE` 语句更新 `users` 表记录：

```sql
UPDATE users SET password = <哈希值>, phone = <手机号>, registed = 1 WHERE uid = <学号/工号>
```

**写入字段说明：**

| 字段 | 值来源 | 说明 |
|------|--------|------|
| `password` | 步骤 7 计算的 SHA-256 哈希值 | 覆盖预置默认密码 |
| `phone` | 用户输入的手机号 | 为用户设置绑定手机号 |
| `registed` | `1` | 标记用户为已注册状态 |
| `uid` | WHERE 条件 | 用户学号/工号，不更新 |

### 5.9 步骤 9 — 系统默认群组创建

注册成功后，系统调用 `ensure_default_groups(uid)` 函数为用户创建以下默认系统群组：

| 群组名称 | 群组类型 | 分类 | 说明 |
|----------|----------|------|------|
| 即时聊天 | `system` | `即时聊天` | 用于与平台所有非好友用户进行临时聊天 |
| 私聊 | `system` | `私聊` | 用于与好友进行一对一私密聊天 |
| 课程 | `system` | `课程` | 按用户角色关联课程聊天室（仅当用户有课程数据时创建） |

**课程群组创建规则：**
- 学生角色：查询 `lesson_stu` 表获取该学生选修的所有课程
- 教师角色：查询 `lesson` 表获取该教师教授的所有课程
- 每门课程创建一个对应的课程聊天室（`groups_chat` 表）

### 5.10 步骤 10 — 注册结果反馈

**注册成功：**
- HTTP 状态码：`201 Created`
- 响应体：`{"message": "注册成功"}`
- 前端弹出提示框"注册成功！请登录"，自动切换到登录表单

**注册失败：** 前端在注册表单错误提示区域（`regError`）展示后端返回的具体错误信息。

## 6. 异常处理

| 异常场景 | 检测时机 | HTTP 状态码 | 返回信息 |
|----------|----------|-------------|----------|
| 密码不符合复杂度规则 | 后端步骤 4.1 | 400 | `密码需包含大小写字母和数字，至少8位` |
| 两次密码不一致 | 后端步骤 4.2 | 400 | `两次密码不一致` |
| 学号/工号在系统中不存在 | 后端步骤 5.1 | 409 | `无该学工号` |
| 学工号与姓名不匹配 | 后端步骤 5.2 | 409 | `学工号与姓名不匹配!` |
| 该学工号已被注册 | 后端步骤 5.3 | 409 | `该用户已注册!` |
| 数据库操作异常 | 后端步骤 8 | 500 | `系统繁忙` |
| 网络错误 | 前端请求 | N/A | `网络错误` |

## 7. 前端行为规范

### 7.1 注册表单元素

- 注册表单 ID：`registerForm`
- 切换方式：通过"登录"/"注册"选项卡切换，切换时清空所有错误提示
- 角色提示区域 ID：`roleHint`
- 错误提示区域 ID：`regError`

### 7.2 注册成功后的行为

1. 调用 `switchTab("login")` 切换到登录表单
2. 清空所有错误提示信息
3. 用户可在登录表单使用注册时设置的密码登录

### 7.3 注册失败后的行为

1. 不清除已填写的表单数据（用户可修正错误后重试）
2. 将后端返回的错误信息显示在错误提示区域

## 8. 数据完整性约束

1. `uid` 在 `users` 表中具有唯一性约束（主键）
2. 一个 `uid` 仅允许进行一次注册（`registed` 从 `0` 变为 `1` 后不可逆转）
3. 密码在传输过程中使用 JSON 明文传输（当前实现无传输层加密——生产环境应使用 HTTPS）
4. 手机号为可选字段，允许为空字符串

## 9. 与外部系统的交互

本功能不直接调用外部系统，验证所需数据来源于：
- `users.json` 文件：系统启动时自动导入数据库
- `lessons.json` 文件：用于课程群组的创建（若存在）
